# disease_cases 검색 컬럼 정규화: 분석 결과와 변환 방법

상태: 개발 DB에 적용 완료(2026-11-07). 운영 DB는 아직 적용하지 않았다.

- 결정: 정규직과 상용직은 별개 범주로 둔다. 비정규직·4대보험 등 고용형태가 아닌 값은 `기타`, work_type의 근무 형태 없는 일정 값도 `기타`로 두고 상세 분류는 후속 작업으로 한다. detail과 범주의 중복은 허용한다.
- 구현: `config/normalization/rules.yml`(규칙), `DiseaseCases::Normalizer`, `rails normalize:report[컬럼]`(미리보기), `rails normalize:disease_cases[apply]`(백필, 기본은 dry-run, 재실행해도 결과 동일), 임포트 rake 연결, 검색 필터(application_type 파이프 경계 매칭, work_type·employment_type 범주 exact match, 옛 표기는 Normalizer로 변환).
- 운영 적용 순서: CSV 백업(`rails export:workercare_data`) → `db:migrate` → `normalize:disease_cases`(dry-run 확인) → `normalize:disease_cases[apply]`.

## 범위

- 대상: `application_type`, `work_type`, `employment_type`, 그리고 빈값 정리(`death_status`, `heavy_lifting`, `work_relevance_eval` 등).
- 보류(후속 작업): `burden_body_part`(동의어·다중값 순서), `job_name`(공백·표기), 근무 시작·종료 시각 구조화.
- 방식: 현재 데이터를 CSV로 백업한 뒤 원본 컬럼을 덮어쓴다(`normalized_*` 컬럼은 만들지 않는다). 덮어쓰면 사라지는 정보는 `*_detail` 컬럼 3개를 새로 만들어 보존한다.

- 괄호 수식어: `유족급여(추정)`, `추가상병신청(폐암)`, `요양급여(미지급보험급여)`.

- 띄어쓰기·어순: `고정주간근무` / `고정 주간근무` / `주간고정근무`.

비어 있지 않은 26,565건 중 distinct 1,583종. 정규직 계열만 수십~수백 종이다(`정규직(상용)`, `정규직(4대보험)`, `정규직(고용승계)` …). 첫 키워드 기준으로 정규 11,780 / 일용 5,951 / 상용 4,843 / 계약 645 / 자영 403 / 파견 213 / 특고·프리 168 / 기타 2,562.

## 2. 변환 방법

공통 절차: NFKC 정규화 → 공백 정리 → 사전 매핑. 사전은 `config/normalization/<컬럼>.yml`에 두고, 사람이 검토한 내용만 쓴다. 사전에 없는 값은 trim만 하고 보존한다.

### 빈값
NULL, `''`, 공백만 있는 값은 모두 NULL로 바꾼다. 허용값 목록 밖의 값도 NULL이다.
주의: "추출 안 함"(NULL)과 "추출했으나 값 없음"(`''`)의 구분이 사라진다. 검색 필터가 둘을 같게 취급하므로 수용한다.

### application_type: `|`로 결합한 다중값 + `application_type_detail`
서식명 접미어("서", "청구서", "신청")를 떼고 아래 8개 토큰을 뽑아 `|`로 결합한다(`burden_body_part`와 같은 파이프 구분 텍스트). 토큰 순서는 표 순서로 고정해서 `유족급여|장의비` 한 가지 표기만 남긴다.

| 토큰 | 인식 대상 |
|---|---|
| 요양급여 | 요양급여, 요양급여신청서, 요양신청서, 요양신청, 최초요양급여신청서, 질병성 요양급여신청서, 진폐요양급여신청서, 요양신청소견서, 추가상병 요양급여 |
| 휴업급여 | 휴업급여 |
| 유족급여 | 유족급여(청구서·신청서·등·(추정)), 유족보상(청구(서)), 진폐유족연금 |
| 장의비 | 장의비, 장례비 |
| 추가상병 | 추가상병(신청(서)), 추가상병 요양급여 |
| 장해급여 | 장해급여 |
| 미지급보험급여 | 미지급보험급여 |
| 재신청 | 뇌심혈관계(질환) 재신청 |

- 결합 예: `요양급여, 휴업급여` → `요양급여|휴업급여`, `유족급여 및 장의비청구서` / `유족급여/장의비` / `장의비 및 유족급여` → `유족급여|장의비`, `추가상병 요양급여` → `요양급여|추가상병`, `진폐유족연금 및 장의비` → `유족급여|장의비`, `요양급여(미지급보험급여)` → `요양급여|미지급보험급여`.
- 8개 토큰에 해당하지 않는 값(`업무상질병`, `업무상 질병 판정` 등 23건)은 토큰 `기타`로 분류한다. 토큰 순서는 맨 뒤다.
- `application_type_detail`(신규, string): 토큰으로 옮기지 못한 원문을 보존한다. 기타는 원문 전체, 토큰이 있는 값은 괄호 수식어(`(추정)`, `(폐암)`)와 잔여 문구. 공백·서식명 접미어 차이뿐이면 NULL.
- 검색: select 옵션은 9개(8개 토큰 + 기타) 고정 목록(distinct pluck 대신 상수, `WORK_RELEVANCE_EVAL_OPTIONS`와 같은 방식). 필터는 부담 신체 부위와 같은 파이프 경계 매칭(`('|' || application_type || '|') LIKE '%|요양급여|%'`)으로 바꾸고 다중 선택은 OR로 처리한다. 인덱스를 쓰지 못하므로 성능은 구현 시 측정한다.

### work_type: 범주 + `work_type_detail`
- `work_type`에는 범주만 남기고, `work_type_detail`(신규, string)에는 범주 키워드를 뺀 나머지(시간, 주 N일, 괄호 내용)를 저장한다.
- 범주 규칙(공백 제거 후 우선순위 순): 격일 → 교대(`N조M교대` 포함) → 야간 → 주간(고정주간·주간고정 포함) → 시간제·파트타임 → 일용 → 기타.
- 예:

| 원문 | work_type | work_type_detail |
|---|---|---|
| 고정 주간근무 | 고정주간근무 | NULL |
| 고정주간근무 (08:00~17:00, 주 5일) | 고정주간근무 | 08:00~17:00, 주 5일 |
| 교대근무 (오전/오후/야간조) | 교대근무 | 오전/오후/야간조 |
| 주 5일 근무 (09:00~18:00) | 기타 | 주 5일 근무 (09:00~18:00) |

- 미분류 8,134건은 기타가 되고 원문이 detail에 남아 정보 손실이 없다.
- 시작·종료 시각의 구조화(`work_start_time`, `work_end_time`)는 형식이 제각각이라 이번에는 보류한다.
- 검색 UI는 텍스트 입력 대신 범주 select + exact match를 쓴다.

### employment_type: 범주 + `employment_type_detail`
- `employment_type`에는 정규직, 상용직, 일용직, 계약직, 파견직, 특수고용·프리랜서, 자영업, 기타 중 하나만 남긴다. 첫 키워드로 분류하고, 분류하지 못하면 기타다.
- `employment_type_detail`(신규, string)에는 괄호 수식어(`(4대보험)`, `(고용승계)`, `(이전 일용직)`)와 분류 키워드 외 나머지를 보존한다. 기타는 원문 전체. 공백 차이뿐이면 NULL.

### 검색 화면 반영 (첫 페이지 `/`, 상세 검색 `/search`)
- 구조화 필터(신청서 종류·고용 형태·근무 형태·업무관련성·사망 여부)를 `_structured_filters` partial로 분리해 두 화면이 함께 쓴다.
- 신청서 종류는 체크박스이고 여러 개를 고르면 OR(하나라도 포함)이다. 둘 다 있는 건만 찾는 AND(모두 포함)는 보류했다. 값이 더 많은 `burden_body_part` 정규화 때 연결 테이블(태그) 방식과 함께 다시 검토한다.
- 상세 검색의 질병분류·신체부위 체크박스는 기본 미선택이고, 고르지 않으면 조건 없이 찾는다. 판정일 라벨은 한글로 고쳤다.
- 근무 형태·고용 형태는 범주 exact match다. 옛 표기가 들어오면 `Normalizer`로 범주로 바꿔 매칭한다(MCP 호환).
- 카카오 챗봇은 이 필터를 쓰지 않아 영향이 없다.

## 3. 진행 순서

1. 이 문서 확인.
2. `rake export:workercare_data`로 CSV 백업(`tmp/`, git 제외). 건수 61,815와 대상 컬럼 값을 확인한다. (완료: `tmp/disease_cases_20261107.csv`, 61,815행, 745MB. DB 건수와 일치.)
3. 군집 탐색 rake(읽기 전용)로 유사 표기 후보를 뽑아 사전 YAML을 만들고 검토한다. 자동 병합 결과를 검토 없이 덮어쓰지 않는다.
4. `Normalizer` + 마이그레이션(`application_type_detail`, `work_type_detail`, `employment_type_detail` 추가) + 백필 rake. dry-run을 먼저 하고, 고유값 단위 `update_all`로 처리하며 여러 번 돌려도 결과가 같게 한다.
5. 재임포트 rake(`import_extracted_disease_cases.rake`)에 Normalizer를 연결해 재임포트해도 원본 표기로 돌아가지 않게 한다.
6. 검색 코드(`main_searchable.rb`, `disease_cases_controller.rb`, `search.html.erb`)를 위 방식으로 변경한다. MCP·챗봇 입력은 Normalizer로 변환해 호환을 유지한다.
7. 테스트와 전후 distinct 수 비교.

## 4. 주의

- 덮어쓰기는 되돌릴 수 없다. CSV 백업 검증 → 사전 검토 → dry-run → 실행 순서를 지킨다. 운영 DB 반영 전에는 다시 확인받는다.
- 재추출·재임포트 파이프라인(`wip/`)이 원본 표기를 다시 만들 수 있으므로 5번 연결이 필수다.
