# 산재알아보기 (단계별 자가진단)

주소 `/self-care-form`. 한 화면에 질문 하나, 큰 버튼 클릭(신체부위·직업은 직접 입력도 가능)으로 단계를 밟고, 고른 조건으로 **비슷한 판정 사례**를 보여 준 뒤 **산재 신청 방법 안내**(`/apply-guide`)로 이어 주는 화면이다.

대상: 신청해야 하는데 하지 않는 사람, 아프기 전에 예방 차원으로 알아보려는 사람, 병원 갈 시간이 부족해 먼저 스스로 찾아봐야 하는 사람(배달·택배·플랫폼 노동자 등).

원칙: **승인 가능성을 예측하지 않는다.** 결과는 "비슷한 판정 사례(참고용)"일 뿐이고 의료·법률 판단을 대신하지 않는다. 화면 어디에도 "인정됩니다/될 가능성이 높습니다" 같은 문구를 쓰지 않는다(테스트가 막는다).

> 기준일: 2026-11-11. 구글 폼에 통계를 보내는 기능은 **켜져 있다**(선택 동의한 사람만, 사용자 결정 2026-11-11, 법률·개인정보 검토는 미실시). 켜고 끄는 방법과 폼 만드는 방법은 10장이다.

## 1. 흐름

```
시작(소개·동의) → 상황 → 신체부위 → 직업(한 화면) → 판정 결과 선택
  → 기초 통계(한 페이지, [건너뛰고 결과 보기]) → 답변 확인 → 결과 → 신청 가이드
```

| 단계 | 경로 | 입력 | 쓰임 |
|---|---|---|---|
| 시작 | `GET/POST /self-care-form` | 필수 동의 체크 | 안내(참고용·예측 아님·개인정보 입력 금지)를 이해했는지 |
| situation | `/self-care-form/situation` | ① 이미 아픈 곳이 있어요 ② 아직 아프지 않지만 예방하려고 알아봐요 ③ 병원 갈 시간이 없어 먼저 알아보고 있어요 · 건너뛰기 | ②는 신체부위를 "걱정되는 곳"으로 묻고 결과 제목이 "같은 일을 하는 사람들의 판정 사례", ③은 결과 위에 가이드의 신청 절차·필요 서류 |
| body_part | `/self-care-form/body_part` | 대표 19개 버튼 + 직접 입력 · 해당 없음 | 검색(부담 신체 부위) |
| job | `/self-care-form/job` | 대표 직종 54개 버튼(5묶음) + 직접 입력 · 모르겠어요 | 검색(직업명) |
| decision | `/self-care-form/decision` | 인정·불인정·일부인정·변경인정·모두 보기 · 건너뛰기 | 검색(판정 결과). 라벨은 DB의 판정 결과 라벨 그대로 |
| profile | `/self-care-form/profile` | 누구의 일·산재 신청 경험·연령대·근무 지역(시·도). 항목마다 "답하지 않음"이 기본 | **통계 전용**. 검색·문구를 바꾸지 않는다(신청 경험이 "불승인을 받음"이면 결과에 불복 절차 링크만 더한다) |
| review | `/self-care-form/review` | 항목별 [바꾸기] | 고른 내용 확인 |
| result | `/self-care-form/result` | | 사례 목록 |

질문 화면은 5개(상황·신체부위·직업·판정 결과·통계)이고 진행 표시는 이 5개만 센다("질문 5개 중 2번째").

의도적으로 **묻지 않는 것**: 성별, 고용 형태, 근무 형태, 시·군·구, KSCO 직업 계층. (KSCO 계층·1순위 필터는 후속 작업이다. 직업은 챗봇 사전의 대표 직종 54개와 직접 입력으로 찾는다.)

## 2. 상태 보관과 개인정보

- 단계별 답은 **암호화된 세션 쿠키**(`session[:self_care_form]`, 브라우저를 닫으면 사라짐)에만 둔다. **서버 DB에는 아무것도 쓰지 않는다**(테스트가 INSERT/UPDATE/DELETE가 없음을 확인한다).
- 답이 URL에 실리지 않는다(접근 로그·브라우저 기록·프록시 로그에 남지 않게). 직접 입력(`free_text`)과 통계 답은 `filter_parameters`로 요청 로그에도 `[FILTERED]`로 남는다.
- 직접 입력은 칸마다 서버에서 **30자로 자르고**(쿠키 4KB 제한 때문), 검색에만 쓴다. 최악의 입력에서도 쿠키는 3KB 미만이다(테스트).
- 세션이 사라지면(브라우저를 닫음·쿠키 차단) 조용히 시작 화면으로 보내지 않고 "진행하던 내용이 사라졌습니다" 안내를 보여 준다.
- [처음부터 다시]는 답과 동의를 지운다(POST).
- 필수 동의 문구는 "직접 식별정보를 입력하지 않도록 안내받았고, 참고용이며 승인 여부를 알려 주지 않음을 이해했다"이다. 개인정보 해당 여부 같은 법률 판단은 이 문서가 단정하지 않는다 `[법률·개인정보 검토 필요]`.

## 3. 직접 입력 규칙

### 신체부위 (`SelfCareForm::BodyPartMatcher`)
`burden_body_part_text` 필터는 부분 일치가 아니라 **파이프 토큰 정확 일치**라 문장 그대로는 0건이 된다. 그래서 입력 문장에서 챗봇 사전(`config/chatbot/entities/body_part.yml`)의 개념을 찾아 그 개념의 토큰(좌우 변형 포함)으로 검색한다.

- 두 글자 이상 표기: 문장(공백 제거)에 **포함**되면 인정하고 가장 긴 표기가 이긴다("왼쪽 손목" → 손목, "경추 디스크" → 목).
- **한 글자 표기**(목·등·손·팔·발·폐·귀·눈·뇌)와 흔한 낱말과 겹치는 표기(`STRICT_SURFACES`: 하지·무지·수지·두부)는 엄격하게: ① 입력 전체(끝의 "통증"·"부위" 등 제외)가 그 표기이거나 ② 낱말 하나가 "그 표기 + 조사"일 때만 인정한다("눈 통증", "눈이 아파요" ○ / "등산 중 다침", "눈물이 남", "일을 하지 못해요" ×).
- 비신체 낱말(`NON_BODY_WORDS`: 사다리·전신주)은 매칭 전에 지운다.
- 못 찾으면 **신체부위 조건 없이** 검색하고 "신체 부위 조건 없이 찾았습니다"라고 알린다(0건을 확정하지 않는다).
- **알려진 한계**: "눈이 많이 와서 넘어짐"은 `눈이`(눈+조사)로 잡힌다. 결과에 "‘눈’(으)로 찾았습니다"가 보이므로 사용자가 알아볼 수 있다.

### 직업
- 버튼은 사전의 **핵심어**(예: 택배기사 → 택배)를 하나라도 직업명에 포함하는 사례를 찾는다(`job_name_any`, 띄어쓰기 무시). 직접 입력은 `job_name` 부분 일치다. 둘 다 있으면 직접 입력이 우선이다.

## 4. 결과와 조건 완화

- 사례 목록은 10건: **질병명, 직업명, 신체 부위, 판정 결과, 심의 연도, 원문 링크, 상세 보기**만 보여 준다. 신청인 주장·판단 근거 같은 **서술형 요약은 노출하지 않는다**(이름·주소를 완전히 거르지 못하기 때문).
- 0건이면 약한 조건부터 뺀다: ① 모든 조건 → ② 판정 결과 조건 제거 → ③ 직업 조건 제거. 신체부위는 끝까지 유지한다. 뺐다면 "조건을 줄여서 찾았습니다: 판정 결과, 직업"을 보여 준다.
- SQL은 시도 수(최대 3) + 건수 1회 이하다. `q`(전문 검색)는 쓰지 않는다.

## 5. "더 자세히 찾기"와 넘어온 조건

결과의 [조건 더 자세히 찾기]는 `/search`로 간다. **버튼으로 고른 값만** 실어 보낸다: 신체부위(펼친 토큰 `burden_body_part[]`), 대표 직종의 핵심어(`job_name_any[]`), 판정 결과(`result`). 직접 입력 원문과 통계 답은 보내지 않는다. 조건을 줄여 찾았다면 **결과를 낸 시도의 조건만** 보낸다.

`/`·`/search`에는 `job_name_any` 입력란이 없고 신체부위 체크박스는 상위 N개뿐이라, 화면에 없는 조건은 위쪽에 **"검색 화면에 없는 조건"**(`_carried_filters`)으로 보여 주고 [직종 조건 빼기]·[신체 부위 조건 빼기] 링크와 hidden 필드로 다시 검색해도 유지한다. 별도 표식 파라미터는 없고 파라미터 모양만 본다.

## 6. 신청 가이드 (`/apply-guide`, `/apply-guide.md`)

본문은 `config/apply_guide/procedure_guides.yml`(신청 절차·필요 서류·불인정 대응·급여 종류·처리 기간)이고 출처·확인일은 파일 위 주석이다. 마크다운을 `redcarpet`로 HTML로 바꾸되 원시 HTML 이스케이프, Rails `sanitize` 허용 목록, `https`·앵커·같은 사이트 링크만 허용한다(`ApplyGuide::HtmlRenderer`). 같은 본문을 `.md`·`Accept: text/markdown`으로도 준다. **출시 전에 공식 출처로 다시 확인한다**(마지막 확인일은 화면 아래에 표시). 특수고용·플랫폼 노동자의 산재보험 적용, 유족급여·장의비 청구 같은 안내는 아직 없다 `[확인 필요]`.

## 7. 웹 접근성 (목표: KWCAG 2.2 / WCAG 2.2 AA 수준)

색 대비, 포커스 표시, 44px 터치 크기, 큰 글씨·고대비 화면 설정의 기준과 구현은 [DESIGN.md](../DESIGN.md)에 있다. 여기서는 되풀이하지 않는다.

이 작업은 접근성을 높이려는 구현 기준이며 "KWCAG 준수"나 웹접근성 품질마크 인증을 주장하지 않는다. 항목별 조문은 NIA 지침 원문으로 대조해야 한다 `[확인 필요]`. KRDS의 라디오·단계 표시 명세와 라이선스는 확인하지 못해 **코드를 복사하지 않았다**. GOV.UK Design System의 패턴(질문 하나·뒤로 가기·답변 확인·`fieldset`+`legend`·오류 요약)만 참고했다.

자동 테스트가 확인하는 것(`test/controllers/self_care_form_controller_test.rb`, `layout_accessibility_test.rb`):
- 모든 페이지: `lang`, 첫 요소가 `main#main`을 가리키는 건너뛰기 링크, `nav[aria-label]`, `main#main`.
- 질문 화면: 번호가 들어간 고유한 `<title>`, `<h1>` 하나(`tabindex="-1" autofocus`), 진행 텍스트와 `progress[aria-label]`, **모든 입력에 연결된 label**, 중첩 form 없음.
- 오류(동의 미체크): `role="alert"` 요약 + 항목으로 가는 링크 + `aria-invalid`·`aria-describedby` + "오류:" 접두 문구.
- 새 창 링크의 "(새 창)" 숨김 텍스트, 세션을 잃었을 때의 안내와 [처음부터] 링크.

## 8. 알려진 한계

- 화면 이름과 문구는 `config/locales/self_care_form.ko.yml`에 있다(영어는 `.en.yml`).
- 사전에 없는 직종·신체부위는 직접 입력으로 찾는다.
- 연령대·시·도·누구의 일·신청 경험은 기본으로 **화면 안에서만** 쓰이고 어디에도 저장되지 않는다. 운영자가 구글 폼 전송을 켠 배포에서만, 시작 화면의 선택 동의에 체크한 사람의 선택이 구글 폼으로 간다(10장). 동의 문구·보관 기간·삭제 주체는 아직 정해지지 않았다.
- [결과 보기]를 빠르게 두 번 눌러 두 요청이 모두 제출 표시 없는 같은 쿠키로 도착하면 구글에 두 번 제출되어 시트에 2행이 생길 수 있다. 저장소 없이 서버만으로 막을 수 없고 JS도 쓰지 않으므로 집계할 때 중복 가능성을 감안한다.

## 10. 구글 폼으로 통계 보내기 (켜짐, 2026-11-11 사용자 결정)

> 확인하지 못한 것: 구글 폼 화면의 메뉴 이름은 바뀔 수 있다(같은 뜻의 메뉴를 찾는다). `formResponse` 직접 제출은 구글의 공식 API가 아니라 폼 제출 주소를 쓰는 비공식 방식이라 **구글이 막을 수 있고 직접 지속성을 검증하지 못했다**. 샘플 폼으로 `send_test`를 한 번 보냈고(2026-11-11, status=200) 시트에서 `[테스트]` 행은 시험한 사람이 확인하고 지운다.

### 10.1 개요

```
(선택 동의한 사용자) [결과 보기] → 우리 서버가 응답을 보낸 뒤 → 구글 폼 formResponse로 POST → 폼에 연결된 구글 시트에 한 행
```

- **켜져 있을 때만**(현재 켜짐) 동작한다. 꺼져 있으면 전송도, 시작 화면의 "통계용 저장" 선택 동의란도 없다.
- 구글로 가는 것: 사용자가 고른 옵션의 **라벨 문자열**(상황·누구의 일·신체부위·직업·판정 결과·신청 경험·연령대·근무 지역, 그리고 폼에 문항이 있으면 조건 완화 여부·결과 건수). **건너뛴 항목은 보내지 않는다.**
- 직종 칸: 버튼으로 고른 대표 직종은 그 이름, **직접 입력은 원문 대신 고정 문구 "직접 입력"**(`self_care_form.stats.job_free_text`; 직접 입력은 사전과 대조하지 않으므로 어떤 직업을 적어도 이 문구다), "모르겠어요"는 그 라벨을 보낸다. 직종 단계에 답하지 않았으면 비어 있다. 신체부위는 아직 같은 처리가 없어 직접 입력이 사전에 안 맞거나 "해당 없음"이면 빈칸이다.
- 폼 필드로 보내지 않는 것: **직접 입력한 원문**, IP, User-Agent, 세션 ID. 다만 서버가 구글을 호출하므로 **구글은 이 서비스 서버의 IP와 요청 메타데이터를 본다**(사용자의 IP가 아니다). "개인정보가 가지 않는다"고 쓰지 않는다.
- 폼의 답은 우리 앱으로 돌아오지 않는다.
- **[결과 보기] POST를 누를 때마다, 마지막으로 보낸 값과 다를 때만** 보낸다(2026-11-11 사용자 결정). 비교는 보낼 값(설정에 문항이 있는 키)의 SHA-256 해시로, 쿠키 `session[:self_care_form_last_digest]`에 해시만 둔다. 결과 화면 새로고침·뒤로 가기(GET)는 보내지 않고, [처음부터 다시]도 해시를 지우지 않아 같은 답이면 다시 보내지 않는다. 구글 요청이 실패해도 같은 답으로는 재시도하지 않는다(해시를 응답 전에 켠다). 콜백 배열이 없어 건너뛴 경우에는 해시를 켜지 않아 다시 시도할 수 있다. **시트의 행은 사람이 아니라 "답 조합 한 번"이다.** 쿠키를 지우거나 다른 브라우저면 같은 답도 다시 가므로 건수는 사용자 수가 아니다.

### 10.2 켜기 전에 정해야 하는 것 (2026-11-11 사용자 결정으로 켬)

2026-11-11에 사용자가 아래와 같이 정하고 `enabled: true`로 켰다.

- **동의는 선택**이다(시작 화면의 `stats_consent` 체크박스). 아무도 강제되지 않고, 동의하지 않아도 모든 기능을 똑같이 쓴다.
- **보관 기간**: 저장한 날부터 최대 3년, 해마다 점검해 필요 없는 행은 지운다. **삭제 담당**: 산업재해 프로젝트 팀. 시작 화면 마지막 줄(`self_care_form.start.stats_retention`)에 이 내용이 들어 있다.
- 수집 항목과 목적(통계), 저장 위치(구글 폼·시트)는 시작 화면 동의 문구와 같다. 시트 접근자는 최소로 한다.
- **법률·개인정보 검토는 하지 않았다.** 사용자가 선택 동의 방식으로 켜기로 결정했을 뿐이고, 검토는 여전히 권장 사항이다 `[법률·개인정보 검토 권장, 미실시]`.
- 연령대·시·도·직업·신체부위·신청 경험의 **조합**은 재식별 위험이 있고 "산재 신청 경험"은 건강·근로와 연결된 정보다. 동의 문구는 "직접 식별정보는 입력하지 않도록 안내하지만 선택 조합에 따라 재식별 위험이 있을 수 있음"을 밝힌다. 개인정보 해당 여부는 이 문서가 단정하지 않는다. 연령대에 10대가 있어 만 14세 미만 정보의 법정대리인 동의 여부도 검토 항목이다(15세 미만은 원칙적으로 취업이 금지라 "10대"는 사실상 15~19세).
- **2026-11-11 전송 범위 변경**: 처음에는 브라우저 세션당 한 번이었으나 사용자가 "답이 달라질 때마다"로 바꿨다. 동의 문구(`stats_once`)가 바뀌었으므로 법률·개인정보 재확인을 권장한다. 시트 행 수(3년 보관)가 늘어난다.
- 끄려면 `config/self_care_form.yml`의 `enabled`를 `false`로 바꾼다.

### 10.3 구글 폼 만들기

1. **새 폼**을 만든다. 제목은 "산재알아보기 설문", 설명에는 "이 폼은 사이트가 자동으로 채웁니다. 직접 열어 쓰지 마세요"를 적는 것을 권한다. 계정은 개인 계정 대신 **팀 공용 계정**을 쓴다.
2. 문항은 **모두 "단답형(짧은 답변)"**이고 **필수가 아니어야** 한다. 섹션은 나누지 않는다(한 섹션). 문항 목록은 아래 명령으로 만든다. 문항 제목은 앱이 보지 않고 **entry id만** 본다.

   ```bash
   bin/rails self_care_form:google_form_spec
   ```
   - 단답형인 이유: 우리가 보내는 문구가 선택지와 달라도 버려지지 않는다. 구글은 **필수 문항이 비면 200을 주고 조용히 버린다**.
   - 체크박스·기타 항목·파일 업로드·멀티 섹션은 쓰지 않는다(인코딩·`pageHistory`를 확인하지 못했고, 파일 업로드는 로그인을 강제한다).
3. **설정**: 응답자 로그인 제한("Google 계정으로 제한")·응답 1회 제한·이메일 주소 수집·응답 수신 확인 메일을 **모두 끈다**. 로그인이 필요하면 서버의 제출이 401로 실패한다.
4. **응답 탭 → 시트에 연결**(새 시트). 시트 공유는 **팀원만**, 링크 공유는 끈다.
5. **entry id 얻기**: 폼 오른쪽 위 ⋮ → "미리 채워진 링크 가져오기" → 문항마다 구별되는 샘플(`A1`, `A2`…)을 넣고 "링크 가져오기" → 주소의 `entry.<숫자>=A1`에서 숫자를 문항과 짝지어 적는다.
6. **제출 주소**: 폼의 공개 주소(`https://docs.google.com/forms/d/e/<폼 ID>/viewform`)에서 `viewform`을 `formResponse`로 바꾼 것이다.

### 10.4 앱에 연결하기

`config/self_care_form.yml`:

```yaml
enabled: true           # false면 전송도 동의란도 없다
google_form_response_url: "https://docs.google.com/forms/d/e/<폼 ID>/formResponse"
entries:                # 앱 키 → entry id(숫자)
  body_part: 123456789
  ...
```

- 앱 키는 `body_part`, `job`, `decision`, `age_band`, `region`, `application_experience`, `respondent`, `situation`, `relaxed`, `result_count` 10개 중에서만 쓴다(`SelfCareForm::Flow::SENDABLE_KEYS`). **`entries`에 id가 있는 키만 전송**하므로 폼에 문항을 더하거나 빼도 코드는 바뀌지 않는다.
- 서버가 이 URL을 호출하므로 **검증을 모두 통과해야 켜진다**: https, 호스트가 정확히 `docs.google.com`, 경로 `/forms/d/e/<ID>/formResponse`, 쿼리·프래그먼트 없음, entries의 키는 위 10개 안에서만, 값은 숫자만. 어긋나면 전송을 끄고 부팅 로그에 이유를 남긴다(값은 적지 않는다). 리다이렉트는 따라가지 않고 3xx도 실패로 취급한다. URL과 id는 요청 파라미터로 바꿀 수 없다.
- 저장소는 **`enabled: true`**(2026-11-11 사용자 결정)이고 `google_form_response_url`과 `entries`에는 **샘플 폼**의 값(아래 샘플 표와 같음)이 들어 있다. 운영 폼을 새로 만들면 폼 ID와 id가 모두 바뀌므로 함께 고친다.

### 10.5 시험 (필수)

1. 설정을 채우고(`enabled`와 무관하게 설정이 올바르면 된다) 시험 행을 한 줄 보낸다.

   ```bash
   CONFIRM=1 bin/rails self_care_form:send_test
   ```
   - 연결된 시트에 **모든 칸이 `[테스트]`로 시작하는 한 행**이 남는다. 설정이 올바를 때만 보낸다.
   - **시험한 사람이 그 행을 시트에서 지운다.** 집계할 때는 `[테스트]` 행을 제외한다. 샘플 폼이 곧 테스트 폼이므로 별도 테스트 폼은 권장 사항이다.
2. **시트에서 직접** 행이 생겼는지 확인한다. 구글은 거부해도 200을 주므로 앱 화면이나 로그로는 알 수 없다.
3. `enabled: true`로 바꾸고 로컬에서 끝까지 진행한다: 선택 동의로 완료하면 1행, 동의하지 않으면 0행, 새로고침해도 1행, 설정을 비우면 동의란이 사라지고 보내지 않는다.

### 10.6 문제 해결

| 증상 | 확인할 것 |
|---|---|
| 행이 안 생김 | 폼에 **필수 문항**이 남음 / 응답자 **로그인 제한** / entry id 오타 / **파일 업로드 문항** 존재 / 폼이 닫힘·응답 중단 / `viewform`→`formResponse` 누락 / 서버 로그의 `status=` |
| 빈 칸만 생김 | entry id와 문항의 짝이 어긋남 |
| 로그에 `status=401` | 로그인 제한이 켜져 있음 |
| 로그에 `전송 실패 (Net::OpenTimeout)` | 구글 응답 지연(타임아웃은 열기·읽기 각 1초). 그 세션은 재시도하지 않는다 |
| 로그에 `rack.response_finished가 없어` | 이 서버가 해당 콜백 배열을 주지 않음. 동기로 부르지 않고 건너뛴다 |
| 부팅 로그에 `구글 폼 전송이 꺼졌습니다` | 설정 검증 실패(이유가 적혀 있음). `enabled`는 true인데 URL·entries가 어긋남 |
| 구글이 막음 | 대안: 결과 화면의 "미리채움 링크로 직접 제출", 구글 시트 API. 교체 지점은 `SelfCareForm::GoogleFormSubmitter` 한 곳 |

### 10.7 개인정보·운영 규칙

- 동의 문구(시작 화면)에 쓰이는 항목: 상황·누구의 일·신체부위·직업·판정 결과·신청 경험·연령대·시·도 중 **폼에 문항이 있는 것**, 목적 통계, 저장 위치 구글 폼·시트, 보관 기간(최대 3년), 동의하지 않아도 모든 기능을 똑같이 쓸 수 있음, [결과 보기]를 눌러 답이 달라질 때마다 전송되고 같은 답은 다시 보내지 않음.
- 시트 접근자는 최소로 하고 해마다 점검해 3년이 지났거나 필요 없는 행을 산업재해 프로젝트 팀이 지운다.
- 집계할 때 **5건 미만인 칸은 가려서** 공유한다. 조합 재식별 위험이 있으므로 원본 시트를 외부에 공유하지 않는다.
- 집계는 시트의 피벗 테이블(상황별·연령대별·시·도별 건수)로 한다. 응답자 구분(본인·유가족·가족·동료)은 따로 본다.
- 질문이나 선택지를 바꾸면 `Flow`, 이 문서, 폼을 함께 고친다. 폼을 새로 만들면 entry id가 모두 바뀐다.

### 10.8 서버 쪽 확인 (2026-11-09)

- 운영은 Thruster → `bin/rails server`(Puma 7.2.0)로 뜨고 Puma는 요청마다 `env["rack.response_finished"]`를 배열로 만든다. 번들의 Rack 3.2.7은 `rack.after_reply`를 정의하지 않으므로 표준인 `rack.response_finished`를 쓴다.
- 번들의 Puma로 최소 Rack 앱을 띄워 확인했다: **응답을 보낸 뒤** 콜백이 실행된다(1초 걸리는 콜백이 있어도 응답 시간은 1ms 안팎), 콜백이 예외를 던져도 다음 요청은 정상이다. 콜백은 응답을 보낸 뒤 **같은 Puma 스레드를 최대 약 2초(타임아웃 합계) 붙잡는다.** Rails 실행기도 같은 배열에 자기 완료 처리를 넣고 Puma가 역순으로 실행하므로 콜백 안의 예외는 모두 삼킨다.
