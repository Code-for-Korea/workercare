## 1. 배경과 문제

업무상 질병 판정서에는 직업, 업무 부담, 의학적 소견과 판단 근거가 기록되어 있지만, 노동자나 상담 활동가가 자신의 상황과 비슷한 사례를 빠르게 찾고 비교하기 어렵다. 산재상담실은 기존 판정서 구조화·검색 성과를 카카오톡에서 더 쉽게 이용하도록 한다.

## 2. 목표

1. 노동자가 일상적인 표현으로 산재 신청 안내와 관련 판정 사례를 찾는다.
2. 상담 활동가가 동일한 사례의 상세 판단 근거와 출처를 확인한다.
3. 기존 workercare 검색 페이지와 데이터·검색 로직을 재사용한다.
4. 실제 승인 가능성을 예측하지 않고, 검증된 자료와 확인해야 할 사항을 안내한다.

### 대상과 범위

- 대상: 노동자, 노동 상담 활동가 모두
- 공개: 첫 버전부터 일반 사용자 공개를 목표로 하되 개인정보·정확성 검증 통과 후 배포
- 입력: 메뉴/바로연결 + 자연어 혼합
- MVP 기능: 산재 신청·절차 안내, 업무상 질병 판정 사례 검색
- 결과 표시: **혼합형** — 쉬운 요약을 기본 제공하고, 상세 근거 보기를 선택할 수 있음
- 제외: 개인별 승인 확률, 의료·법률 판단 자동화, 계정 기반 상담 이력, 카카오싱크, Event API

## 3. 서비스 경험 원칙

- **최소 단계:** 사용자 유형을 먼저 고르도록 강제하지 않는다. 첫 질문에서 바로 검색할 수 있다.
- **필요할 때만 되묻기:** 질병명, 직종, 작업 내용이 충분하면 즉시 검색하고, 모호할 때만 추가 질문한다.
- **설명 수준 선택:** 노동자용 쉬운 설명을 기본으로, 상담 활동가용 상세 필드와 근거를 선택 제공한다.
- **검색과 판단 구분:** 비슷한 사례는 참고자료이지 본인의 승인 가능성을 뜻하지 않는다.
- **출처 표시:** 사례마다 사건번호(`case_no`)와 기존 웹 상세 페이지 링크를 제공한다.
- **언제든 복귀:** 처음으로, 다시 검색, 조건 변경, 도움말을 지속적으로 제공한다.

## 4. 사용자 시나리오

### A. 노동자의 판정 사례 검색

1. 사용자: “12년 동안 자동차 부품을 조립했는데 회전근개파열 진단을 받았어요.”
2. 봇: 질병명과 업무 설명을 인식하고, 필요한 경우 어깨 부담 작업 여부를 한 번 묻는다.
3. 봇: 관련 사례의 판정 결과와 핵심 고려 요소를 짧게 표시한다.
4. 사용자: “판정 이유 보기” → 상세 요약 또는 기존 workercare 판정서 상세 페이지로 이동한다.
5. 사용자: “다른 사례 보기” 또는 “검색 조건 바꾸기”를 선택한다.

### B. 상담 활동가의 상세 검색

1. 사용자: “물류 노동자 허리디스크 불인정 사례 찾아줘.”
2. 봇: 질병·직종·판정 결과를 추출해 검색한다.
3. 봇: 관련 사례를 제시한다. 사용자: “상세 정보 보기”.
4. 봇/웹: 업무 내용, 작업 부담 요인, 판단 근거(위원회 판단)를 보여준다.

### C. 산재 신청 절차 안내

1. 사용자: “산재 신청하려면 무엇부터 해야 하나요?”
2. 봇: 신청 절차 안내를 제공하고 준비 서류·신청 방법·상담 안내로 연결한다.
3. 안내에는 출처, 확인일, 적용 시점을 표시한다.

### D. 모호한 질문·검색 결과 없음

- “허리가 아픈데 산재 되나요?” → 승인 여부 단정 대신 진단명 또는 주요 작업에 관한 짧은 질문.
- 조건에 맞는 사례가 없으면 ‘사례 없음’과 ‘판단 불가’를 구분하고 검색 조건 완화를 제안.
- 이해하지 못한 질문은 폴백과 홈/도움말로 연결.

## 5. 카카오 시나리오·블록

| 논리 ID | 이름 | 주요 역할 | 권장 구현 |
|---|---|---|---|
| HOME | 처음으로·도움말 | 주요 메뉴, 개인정보 주의 | 정적 블록, 바로연결 |
| CASE_SEARCH | 판정 사례 검색 | 자연어/엔티티 추출, 조건부 되묻기 | 엔티티·파라미터·스킬 |
| CASE_RESULT | 검색 결과 | 검색 요약, 대표 사례 | 스킬 응답(별도 블록은 선택) |
| CASE_DETAIL | 판정 상세 | 판단 근거와 출처 | 스킬 + 웹 링크 |
| CASE_REFINE | 검색 조건 변경 | 이전 조건 일부 변경 | 카카오 컨텍스트(조건 보관) — 개발계획 §5.4 |
| GUIDE | 산재 제도 안내 | 절차·서류·FAQ | 정적 안내/스킬 |
| COUNSEL | 추가 상담 | 사람에게 상담 요청 | 운영 준비 시 상담직원 연결 플러그인 |
| NO_RESULT | 결과 없음 | 조건 완화·새 검색 | 스킬 응답 |
| FALLBACK | 이해하지 못한 질문 | 도움말·홈·재질문 | 폴백 블록 |

실제 관리자센터 블록 ID는 생성 후 매핑한다. `CASE_RESULT`·`NO_RESULT`는 독립 블록이 아니라 검색 스킬의 응답 분기일 수도 있다.

### 권장 고정 메뉴

- 판정 사례 찾기
- 산재 신청 안내
- 처음으로 / 도움말

### 바로연결

검색하기, 상세 보기, 조건 바꾸기, 다른 사례 보기, 처음으로, 도움말. 응답 이후에도 내비게이션이 끊기지 않게 한다.

## 6. 엔티티·파라미터

| 엔티티 | 예시 | 처리 원칙 |
|---|---|---|
| disease_name | 회전근개파열, 손목터널증후군, 허리디스크 | 동의어 인식. 데이터에 KCD 코드 컬럼이 없으므로 코드 안내는 하지 않는다 |
| job_name | 용접원, 조립원, 물류 노동자 | 업종과 직종 구별; KSCO 추정 확정 금지 |
| work_factor | 반복 동작, 중량물, 팔 거상 | 자유로운 작업 설명도 허용 (자유 텍스트 검색) |
| decision_type | 인정, 불인정, 일부인정, 변경인정 | 한글 표현을 DB 값(enum)으로 변환해 보존 |

### 엔티티 → 기존 검색 파라미터 매핑

기존 웹 검색은 두 경로가 있다. 메인(`/`)은 `main_search_params`, 상세(`/search`)는 `search_params`를 쓴다. 챗봇은 `DiseaseCase.main_search` 한 경로만 사용한다. 다만 `main_search`의 전문 검색(FTS) 대상 컬럼은 `job_name`, `job_description`, `main_reasoning`, `other_harmful_factors`, `aggravating_factors`이고 `disease_name`은 포함되지 않으며 폴백도 `job_name`/`job_description`만 검색한다. 그래서 `apply_main_filters`에 `disease_name`(LIKE)과 `result`(enum 일치) 필터를 추가해 사용한다(개발계획 §5.0). 레거시 `DiseaseCase.search`는 쓰지 않는다.

| 엔티티/조건 | 사용할 검색 파라미터 | 비고 |
|---|---|---|
| disease_name | `disease_name` (신규 LIKE 필터) | `q`에 넣지 않는다. 증상만 말한 경우는 `q`(작업·소견 텍스트 검색)로 보조 |
| job_name | `job_name` (LIKE 부분 일치) | `ksco_code[]`는 사용자가 코드를 직접 줄 때만 선택적으로 사용 |
| work_factor | `q` (FTS: 업무 설명·판단 이유·기타 유해 요인·악화 요인) 또는 `burden_body_part_text` (LIKE) | 정확 일치가 아님을 전제. 정규화 사전 없음 |
| decision_type | `result` (신규 enum 필터) = `approved` / `rejected` / `partially_approved` / `revised_approved` | 인정→approved, 불인정→rejected, 일부인정→partially_approved, 변경인정→revised_approved, “전체”→필터 없음 |
| 근무기간 | (필터 없음) | 컬럼 `job_tenure_months`는 있으나 기존 검색 필터가 없다. MVP는 검색 조건이 아니라 **결과 표시 항목**으로만 사용하고, 필터는 후속 과제로 둔다 |

- 위에 없는 값은 무시하고 사용자에게 “이 조건은 아직 검색에 사용할 수 없다”고 안내한다.
- 모든 파라미터를 필수로 요구하지 않는다. 질병명을 모르면 증상·작업으로 검색하는 별도 경로를 제공한다.
- 되묻기: 처음에는 최대 2회 권장, 만료 시간은 카카오 설정 범위에서 30분 시범 적용.
- '모르겠어요'는 질병 엔티티 값이 아니라 별도 흐름으로 처리한다.
- 엔티티 CSV는 UTF-8로 관리하며 기존 판정서 용어집과 연결한다.

## 7. 검색 결과 표시 — 혼합형

### 기본 응답(모든 사용자)

- 검색 조건 요약과 표시 건수(전체 건수와 화면 건수 구분). 기존 검색은 결과 상한이 있어 상한 도달 시 정확한 전체 건수를 표시하지 않는다(`over_cap`).
- 대표 사례 1~3건: 질병명·업무(직종)·판정 결과·핵심 판단 요소
- `상세 정보 보기` / `검색 조건 바꾸기` / `다른 사례 보기`
- 주의: ‘검색 결과는 개인의 산재 승인 가능성을 의미하지 않습니다.’

### 상세 응답(선택)

- 질병명, 직종명(및 연결된 KSCO가 있으면 KSCO), 업무 설명, 근무기간(`job_tenure_months`), 작업 부담 요인
- 인정/불인정/일부인정/변경인정 결과
- 위원회 판단·판단 이유(`main_reasoning`)와 사건번호(`case_no`)
- 기존 workercare 판정서 상세 웹페이지(`/disease_cases/:case_no`) 연결

카카오톡에서는 텍스트 중심 요약과 대표 사례 카드를 사용한다. 이미지 없는 카드 표시·버튼 수·캐로셀 제한은 관리자센터와 실제 스킬 규격에서 검증한다. 긴 근거는 웹에서 읽도록 한다.

## 8. 기존 workercare 연동 원칙

기준 저장소: https://github.com/Code-for-Korea/workercare

현재 브랜치 코드 실사로 확인한 구성(2026-10-10):

- 라우트: 메인 `/`, 검색 `/search`, 판정서 상세 `/disease_cases/:case_no` (`config/routes.rb`, 식별자는 `case_no`이며 `:id`가 아니다).
- 검색: 별도 서비스 클래스는 없고 `DiseaseCase` 모델 concern의 `DiseaseCase.search`(`DiseaseCases::Searchable`), `DiseaseCase.main_search`·`apply_main_filters`(`DiseaseCases::MainSearchable`)를 사용한다.
- 직렬화: `DiseaseCase#as_safe_json`이 `PIIMasking`을 적용하며 MCP 상세 리소스만 사용 중이다. 웹 상세(`show`)는 마스킹 없이 필드를 그대로 출력한다.
- MCP 검색·절차 안내 기능은 `app/mcp` 하위에 있으며 챗봇이 직접 쓰는 것은 아니다.

단계:

- 1차: 카카오 블록에서 기존 검색 페이지로 연결해 사용자 흐름 검증.
- 2차: 동일 Rails 애플리케이션의 모델 검색 메서드를 스킬 어댑터에서 재사용해 채팅창에 결과 표시.
- 3차: 상세 비교·증거 자료 안내 등 기존 MCP 기능의 내부 로직 공유 검토.
- MCP 프로토콜을 불필요하게 경유하지 않고 동일 앱 내부 모델·서비스를 직접 호출하는 방식을 우선한다.

## 9. 공개·안전 기준

- **공개 범위(확정):** 보유한 판정서 데이터는 모두 개인정보를 기호(문자)로 대체해 비식별 처리한 상태이므로, 레코드별 공개/검증 플래그를 두지 않고 전체 사례를 공개 대상으로 본다.
- **비식별은 적재 단계의 책임이다.** 원본 데이터는 이미 식별 처리를 마쳤고, 신규 적재 데이터도 같은 기준을 충족해야 한다. 예외적으로 누락이 신고되면 해당 `case_no`를 DB에서 수정하거나 삭제한다. 검색·상세는 DB를 읽고 검색 인덱스(FTS)는 트리거로 동기화되므로 즉시 반영된다.
- `PIIMasking`은 주민번호·전화번호·이메일·계좌번호 **형태**만 `***`로 바꾸는 보조 장치다. 이름·주소 같은 서술형 개인정보는 걸러내지 못하고, 현재는 MCP 상세 리소스(`as_safe_json`)에만 적용되며 웹 상세에는 적용되지 않는다. 웹 상세에 적용할지는 후속 과제로 둔다. 챗봇 응답은 허용 필드 목록(화이트리스트)으로만 직렬화한다(개발계획 §5.2).
- 근거 문장이 없는 항목은 생성하지 않는다. LLM이 판정 이유를 만들어 내지 않는다.
- 노동자/상담 활동가 모드는 **표현 수준**만 바꾸며 접근 권한을 바꾸지 않는다.
- 이름·주민등록번호·전화번호·진료 기록 원문 등 민감정보 입력을 피하도록 안내한다.
- **입력 원문 로깅 금지:** 사용자가 입력한 자연어(이름·진단명·병력 포함 가능)는 챗봇 경로에서 저장·로깅하지 않는다. 기존 웹 검색이 `params[:q]`를 그대로 로깅하는 점은 같은 기준으로 정리한다(개발계획 §9).
- 제도 안내는 공식 출처, 확인일, 적용 시점을 기록하고 주기적으로 검토한다.
- 상담직원 연결은 실제 인력, 운영 시간, 개인정보 처리 방침이 준비된 경우에만 활성화한다.

## 10. MVP 성공 기준(초기 목표, 테스트로 조정)

- 검색·안내·폴백의 핵심 시나리오가 모바일 카카오톡에서 완료된다.
- 평가 질문 100개 이상(절차·검색·모호한 질문·안전·개인정보 포함)을 검증한다.
- 검색 결과의 판정 결과가 모든 테스트 표본에서 원본 판정서(`case_no`)와 일치한다.
- 응답에 개인정보(비식별 누락)가 노출되지 않는다.
- 잘못 해석된 질병·직종을 수정하거나 건너뛸 수 있다.
- 검색 실패·응답 시간 초과·컨텍스트 만료 시 복귀 경로가 제공된다.

## 11. 미확정 사항

실사로 확정: 라우트(`:case_no`), 검색 파라미터와 메서드, 모델 필드, 공개 범위(전체 공개).

남은 항목:

1. 카카오 스킬 요청/응답의 현재 제한과 실행 시간, 카드·캐로셀 지원 범위, 요청 인증 방식.
2. 상담직원 연결의 실제 운영 여부.
3. 상세 페이지의 외부 공유(링크 공유·크롤링) 정책.
4. 공식 절차 안내 자료의 관리 책임자와 갱신 주기.
5. 검색 조건 변경용 세션 저장 방식(개발계획 §5.4 권장안 승인 필요).
6. 근무기간 필터를 추가할지 여부(기본: 후속 과제). 판정 결과·질병명 필터는 `apply_main_filters`에 추가하기로 확정.
