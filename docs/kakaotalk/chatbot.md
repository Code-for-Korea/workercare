## 2. 구현 완료 내역

### 2.1 `show` 404 (`50979a6`)

- `DiseaseCasesController#show`가 `find_by!`를 쓴다. 없는 `case_no`는 404를 반환한다.
- 테스트: 존재하는 사례 표시, 없는 `case_no` 404.

### 2.2 검색 필터 추가 (`c37b099`)

- `DiseaseCase.apply_main_filters`에 추가:
  - `disease_name`: `LIKE` 부분 일치. `main_search`의 전문 검색(FTS) 대상 컬럼에 질병명이 없어 `q`로는 찾을 수 없기 때문이다.
  - `result`: enum 값 일치(`approved`, `rejected`, `partially_approved`, `revised_approved`).
- `main_search_params` 허용 목록에 두 값을 추가했다. 웹 검색 화면에는 입력을 노출하지 않았다.
- **기존 버그 수정:** `q`와 `job_name`을 함께 쓰면 `ambiguous column name: job_name` SQL 오류가 났다. FTS 가상 테이블에도 같은 컬럼이 있기 때문이다. 필터의 컬럼을 `disease_cases.` 접두어로 한정해 해결했다.
- 테스트: 질병명 부분 일치, enum 4종 각각, 질병·직종·`q`·결과 동시 적용(AND), FTS 폴백 시 필터 유지.

### 2.3 스킬 서버 뼈대 (`2103f86`)

| 구성 요소 | 위치 | 역할 |
|---|---|---|
| 라우트 | `config/routes.rb` | `POST /webhooks/kakao` |
| `Webhooks::KakaoController` | `app/controllers/webhooks/kakao_controller.rb` | 인증, 요청 파싱, 응답, 로깅 |
| `Chatbot::KakaoRequestAdapter` | `app/models/chatbot/` | 카카오 payload → 내부 검색 조건 |
| `Chatbot::CaseSearch` | `app/models/chatbot/` | `main_search` 호출, 페이지·건수 계산 |
| `Chatbot::PublicCase` | `app/models/chatbot/` | 공개 DTO(허용 필드만) |
| `Chatbot::KakaoResponseBuilder` | `app/models/chatbot/` | 카카오 `version: "2.0"` 응답 생성 |

설계 결정과 이유:

- **`ActionController::API` 상속.** 카카오 요청에는 CSRF 토큰이 없다. `ActionController::Base`를 쓰면 운영에서 422가 난다. 테스트 환경은 CSRF 보호가 꺼져 있어 테스트로는 놓치기 쉬우므로, 보호를 켠 상태로 요청하는 테스트를 따로 두었다.
- **요청 본문은 `raw_post`를 직접 파싱.** 카카오 payload의 최상위 `action` 키가 Rails 라우팅의 `params[:action]`과 충돌한다.
- **항상 HTTP 200과 유효한 응답 본문.** 결과 없음, 잘못된 입력, 예외 모두 안내 응답으로 처리한다. 카카오 응답 타임아웃(5초)은 고정이다.
- **사례는 `listCard`로 보여 준다.** 처음에는 `textCard` 캐로셀(3건)이었으나 한 번에 10건을 목록으로 보여 주도록 바꿨다(§3.3). `basicCard`는 썸네일이 필수라 쓰지 않는다.
- **바로연결은 `action: "message"`만 사용.** 실제 블록 ID가 아직 없다. 바로연결은 엔티티를 다시 추출하지 않으므로 조건을 `extra`에 실어 `clientExtra`로 이어받는다.

## 3. 스킬 서버 계약

### 3.1 요청에서 읽는 값

| 값 | 위치 | 용도 |
|---|---|---|
| `disease_name` | `action.params` | 질병명 필터 |
| `body_part` | `action.params` | 신체부위. 사전으로 DB 토큰들(+좌우 접두)로 확장해 `burden_body_part` 필터로 검색(§6.7) |
| `job_name` | `action.params` | 직종 필터 |
| `job_names` | `action.clientExtra`(직종 검색 스킬의 `선택한 직종으로 찾기` 버튼) | 고른 직종 이름들. DB 이름 그대로 띄어쓰기를 무시하고 일치(OR). 엔티티 파라미터로는 받지 않는다 |
| `work_factor` | `action.params` | 작업 요인. `q`(전문 검색)로 전달 |
| `decision_type` | `action.params` | 판정 결과. 한글→enum 변환 |
| `page`, 위 조건들 | `action.clientExtra` | 바로연결 버튼으로 이어받는 조건과 페이지 |
| `userRequest.user.id` | | 해시(SHA-256)만 계산. 검색 세션 도입 시 소유권 검증용 |

- 엔티티 값은 `action.params`만 읽는다. `detailParams`의 `origin`은 발화 조각 원문이라 읽지 않는다.
- `userRequest.utterance`(발화 원문)는 읽지 않는다.
- 조건 우선순위: `action.params`의 값이 있으면 그 값, 없으면 `clientExtra`의 값.
- 값은 앞뒤 공백을 제거하고 100자로 자른다. 페이지는 0~100으로 제한한다.
- 값이 `모름`이거나 `#`·`$`로 시작하면(단계별 사례 찾기에서 건너뛴 단계, 해석되지 않은 컨텍스트·엔티티 참조) **조건 없음**으로 보고 버린다. 이 때문에 `모름`은 알 수 없는 판정 값으로 안내되지 않는다.

### 3.2 판정 결과 변환

| 입력 | 결과 |
|---|---|
| 인정 / 불인정 / 일부인정 / 변경인정 | `approved` / `rejected` / `partially_approved` / `revised_approved` |
| enum 값 그대로 | 그대로 사용(`clientExtra` 경로) |
| 전체 / 모두 / 상관없음 / all | 필터 없음 |
| 그 외 | 필터를 버리고 응답에 "인식하지 못해 제외했다"고 안내 |

이 대표 엔트리 이름(인정·불인정·일부인정·변경인정·전체)은 `decision_type` 엔티티와 반드시 일치해야 하며, 테스트가 이를 검사한다(§6.2).

### 3.3 응답

| 상황 | 응답 |
|---|---|
| 조건이 하나도 없음 | 질병명·직종·작업 내용을 묻는 안내. 개인정보 입력 주의 문구 포함. 바로연결 `단계별로 찾기`, `직종으로 찾기`(각각 messageText 동일)와 `처음으로` |
| 결과 있음 | ① 조건 요약·건수·승인 가능성 아님 안내(`simpleText`) ② 사례 목록(`listCard` 최대 2장, 5건씩, 한 번에 최대 10건) |
| 결과 없음 | "찾지 못했습니다"(사례가 없다는 뜻이며 승인 여부 판단이 아님을 명시) + 조건 바꾸기·처음으로 |
| 오류 | 일시적 문제 안내 + 처음으로 |

- 목록: `listCard` 한 장의 header는 `1~5번째 사례`, `6~10번째 사례`(하나만 남으면 `6번째 사례`). 항목은 5건씩이다.
  - **제목(30자) = `직업명 · 신청인 주장`** (예: `기계수리원 · 약 37년 10개월 가량 석탄광업소에서…`). 제목이 설명(16자)보다 글자 수가 많아 긴 내용을 제목에 둔다.
    - 직업명은 10자까지만 쓴다(`건설 및 광업 단…`). 긴 직업명이 주장의 자리를 밀어내지 않게 하려는 것이다.
    - 직업명과 주장 중 **있는 것만** 쓴다. 둘 다 없을 때만 질병명을 쓴다(제목은 비면 안 되므로 마지막 수단. 개발 DB 260건, 0.4%).
    - 주장은 글머리표(`○`, `가.`), 머리말(`신청인 주장 -`, `<신청인의 주장>`, `신청인의 주요 주장은`), 주어(`신청인은`) 같은 상투적 시작을 걷어 내용부터 보이게 한다. 머리말 뒤에 글머리표가 한 번 더 나오는 경우(약 5%)도 걷는다.
    - 날짜(`2018.5.1.부터`)와 비식별 마스킹 이름(`○○○○○에서는`)은 지우지 않는다. 글머리 번호는 "1~2자리 숫자 + 공백"일 때만, `○`는 뒤에 또 마스킹 기호가 이어지지 않을 때만 글머리표로 본다.
    - `PIIMasking`으로 번호 형태 개인정보를 가린다(DTO `claim_summary`).
  - **설명(16자) = `승인여부·신체부위`** (예: `일부인정·어깨,팔꿈치,손목`). 자리가 좁아 구분자를 공백 없는 `·`로 쓴다. 판정 결과를 맨 앞에 둬서 길어서 잘려도 핵심이 남는다.
    - 신체부위는 `burden_body_part`(파이프로 이어진 값)에서 좌우 구분(우측·좌측·양측)을 떼고 중복을 합쳐 앞의 셋까지 쓴다.
    - 신체부위가 없으면 **승인여부만** 보인다(개발 DB의 33.9%, 대부분 뇌출혈·지주막하출혈처럼 신체부위가 해당 없는 질병). 다른 컬럼으로 채우지 않는다: `body_part`(enum)는 그중 6,788건만 채워져 있고 한글 라벨 없이 `arm`, `lower_back` 같은 영문 분류라 `어깨`·`허리` 같은 세부 값과 단위가 다르다.
    - 제한을 넘으면 마지막 항목을 남은 자리에 맞춰 줄이고(`…`) 멈춘다. 말줄임표 앞에 공백이 남지 않게 한다.
  - 항목을 누르면 **근로복지공단 판정서 사이트**(`https://jilbyungcase.comwel.or.kr/service/dataView?id=<사건번호>`)가 열린다. 사례마다 저장된 `link` 컬럼을 쓰고(개발 DB 61,815건 전부 채워져 있고 사건번호로 조립한 주소와 일치), 비어 있을 때만 사건번호로 같은 형식을 조립한다. `https`가 아닌 저장 링크는 쓰지 않는다. 별도 버튼은 없다.
  - 이 구성에서는 **사건번호와 질병명이 목록에 보이지 않는다**(제목이 비는 드문 경우만 예외). 링크를 열어야 알 수 있다.
- `listCard` 글자 수 규격은 `main_notions/setup_answer.md`의 '말풍선 제작 스펙 정보'(모바일톡, 공백 없는 한글 기준)에 있다. **공백·이모티콘이 있으면 덜 들어갈 수 있고**, 규격을 넘으면 말풍선이 정상 동작하지 않을 수 있다고 안내한다. `skill_guide`의 JSON 명세에는 이 제한이 없어 처음에는 35/30으로 추측했는데 규격을 넘는 값이었다. 규격으로 바로잡았다.
- 글자 수가 더 많은 제목(30자)에 `직업명 · 신청인 주장`을, 설명(16자)에 `승인여부·신체부위`를 둔다. 주장은 그래도 대부분 잘린다(주장 길이 p90이 367자). 규격이라 코드로 늘릴 수 없다. 더 길게 보이려면 `textCard` 캐로셀(skill_guide 기준 설명 128자, 10장까지, 옆으로 넘김) 같은 다른 말풍선을 써야 한다(결정 §14-13).
- **미검증:** `setup_answer.md`는 관리자센터 응답에서 "리스트형 말풍선은 하나의 말풍선만 노출할 수 있습니다"라고 안내한다. 스킬 응답에서 `listCard`를 `outputs`에 두 개 두는 것이 허용되는지 확인하지 못했다. 안 되면 `listCard` 하나(5건) 또는 `listCard` 캐로셀(카드 5장 × 4개)로 바꿔야 한다. 봇 테스트 T21에서 확인한다.
- 한 번에 보여 주는 개수는 `Chatbot::CaseSearch::PAGE_SIZE`(10)다. 요약 `simpleText` 1개 + `listCard` 2장이 `outputs` 한도(3개)라 이보다 늘리려면 요약을 `listCard` header에 합치는 등 구성을 바꿔야 한다(테스트가 한도를 검사한다).
- 건수: 결과가 500건 이상이면 정확한 건수를 표시하지 않는다(웹 검색의 상한과 동일).
- 바로연결(`quickReplies`):

| 라벨 | `messageText` | `extra` |
|---|---|---|
| 다른 사례 보기 (다음 페이지가 있을 때만) | `다른 사례 보기` | 현재 조건 + `page + 1` |
| 조건 바꾸기 | `검색 조건 바꾸기` | 현재 조건 |
| 처음으로 | `처음으로` | 없음 |

### 3.4 카카오 제한과 코드 대응

| 항목 | 제한 | 코드 |
|---|---|---|
| `outputs` | 1~3개 | 최대 3개(요약 1 + `listCard` 2) |
| `quickReplies` | 10개 이하 | 최대 3개 |
| `simpleText` | 1000자 | 잘라서 사용 |
| `listCard` 항목 수 | 말풍선 하나에 5개(캐로셀이면 4개) | 5건씩 두 장 |
| `listCard` header | **15자**(규격) | `LIST_HEADER_LIMIT = 15` |
| `listCard` 항목 제목 | 설명이 있으면 **30자**(규격) | `LIST_ITEM_TITLE_LIMIT = 30` |
| `listCard` 항목 설명 | **16자**(규격) | `LIST_ITEM_DESCRIPTION_LIMIT = 16` |
| 응답 시간 | 5초 고정 | 10건 조회. 개발 DB에서 결과 500건 이상인 검색이 약 0.1초 |

### 3.5 직종 검색 스킬 (`POST /webhooks/kakao/jobs`)

직종 검색어로 DB의 **실제 직종 이름** 후보를 보여 주고, 여러 개를 골라 판정 사례를 찾게 한다. 인증은 판정 사례 스킬과 같은 헤더(`X-Skill-Token`)·같은 값이다.

**흐름**
```
직종으로 찾기 ─▶ 직종 입력 ─▶ [후보 목록 10개: 이름 + 사례 수]
                                  ├ 항목 누름 ─▶ 선택에 추가(다시 누르면 빠짐, ✓ 표시)
                                  ├ 직종 더 보기 / 이전 직종 ─▶ 쪽 이동(선택 유지)
                                  └ 선택한 직종으로 찾기 ─▶ 판정 사례 검색 스킬(job_names) ─▶ 사례 목록
```

**요청에서 읽는 값**
| 값 | 위치 | 용도 |
|---|---|---|
| `keyword` | `clientExtra`(후속 요청) → `action.params`(**파라미터 `keyword`에 엔티티 `job_name`을 연결한 블록 파라미터**, 스킬 테스트) → `userRequest.utterance`(**선택 사항**, 입력 대기 컨텍스트 `job_kw`가 있을 때만) | 검색어. 이 순서로 찾는다 |
| `selected` | `clientExtra` | 지금까지 고른 직종 이름들(최대 10개) |
| `pick` | `clientExtra` | 이번에 누른 직종. 이미 선택돼 있으면 빼고, 아니면 더한다 |
| `page` | `clientExtra` | 후보 쪽(0~19, 10개씩) |

- **선택 상태는 서버에 저장하지 않는다.** 항목·버튼의 `extra`로 이어 간다. 항목은 고정 문장 `직종 선택`을 보내고, 어떤 직종인지는 `extra.pick`에 싣는다(직종 이름이 제각각이라 블록 발화로 등록할 수 없기 때문).
- **엔티티 방식이 기본이다.** 카카오가 `action.params.keyword`로 보내는 값은 사용자가 친 단어가 아니라 **대표 엔트리**(`조리` → `조리원`)이고 발화 원문은 읽지 않는다. **자유 입력은 선택 사항**이며, 이 경로를 쓸 때만 아래처럼 발화 원문을 읽는다.
- **자유 입력 경로에서만 발화 원문을 읽는다**(입력 대기 컨텍스트가 있을 때만). 컨텍스트 없는 발화를 검색어로 쓰지 않으므로 폴백 블록에 연결해도 엉뚱한 문장을 검색하지 않는다. 직접 쓰는 로그에는 검색어·직종 이름을 남기지 않고(요청 ID, 출처, 후보·선택 개수, 쪽, 처리 시간만) 테스트로 확인한다.
- **대표 엔트리는 사전의 핵심어로 넓혀 찾는다**(`Chatbot::JobExpansion`). `조리원` → `조리·주방·급식·음식서비스·음식관련`으로 찾아 조리원(908건)·조리사(493건)·주방 보조(170건) …이 후보에 들어온다. 넓히지 않고 `조리원`이라는 글자 그대로 찾으면 후보 109개에서 조리사가 빠지고, 버스기사는 9개뿐이다(넓히면 166개). 대표 54개 모두 후보를 낸다(후보 수 최소 13, 중앙값 149). 공백이 있는 대표(`자동차 조립원`)도 공백을 무시하고 찾는다. 사전에 없는 단어는 아래 토큰 검색으로 처리한다. 이때 쪽 이동 같은 후속 요청에서도 같은 확장이 되도록 `extra.keyword`에는 사용자가 친 말이 아니라 **대표 그대로** 싣는다.
- 사전에 없는 검색어(자유 입력 경로 등)는 구두점을 없애 30자로 자르고 공백으로 나눈 뒤 **두 글자 미만 토큰과 말투 단어**(`직종`, `검색해줘`, `하는데요`, 끝의 `이요`·`이에요` 등)를 뺀다. 토큰은 최대 3개이고 어느 하나라도 부분 일치하면 후보다.
- 후보 = 검색어에 부분 일치하는 서로 다른 `job_name`. **띄어쓰기만 다른 이름은 하나로 묶고** 사례가 많은 순(같으면 이름순)으로 최대 200개까지 가져와 10개씩 보여 준다. 개발 DB에서 처리 시간은 약 7~80ms다.

**응답**
- `outputs` 3개: 요약 `simpleText`(검색어·범위·선택 목록) + 후보 `listCard` 2장(5개씩). 항목 제목은 직종 이름(선택했으면 앞에 `✓ `), 설명은 `N건`. 글자 수는 판정 사례 목록과 같은 `listCard` 규격(§3.4)을 따른다.
- 바로연결: `선택한 직종으로 찾기`(선택이 있을 때만, `extra.job_names`), `직종 더 보기`, `이전 직종`, `직종 다시 검색`(`직종으로 찾기`), `처음으로`.
- 응답마다 출력 컨텍스트 `job_kw`(수명 1, 유효 10분)를 다시 설정하도록 `context`를 싣는다. **블록에 같은 이름의 출력 컨텍스트가 선언돼 있어야** 반영되고(카카오 문서), 그래야 후보를 본 뒤에도 다시 입력할 수 있다.
- 후보가 없으면 `찾지 못했어요`, 검색어가 없거나 한 글자뿐이면 입력 안내를 보낸다. 오류도 HTTP 200과 안내 응답이다.

**판정 사례 검색 스킬 쪽 변경**
- `job_names`(`clientExtra`)를 받아 **DB 이름 전체 일치(띄어쓰기 무시)의 OR**로 거른다. `급식조리원`은 `조리원`을 골라도 포함되지 않는다. 공유 필터 `apply_main_filters`에 `job_names` 항목을 더했고 웹 검색 화면은 이 값을 받지 않는다.
- 요약에 `직종 조리원, 조리사`(3개를 넘으면 `외 N`)가 보이고 `다른 사례 보기`가 `job_names`를 이어 간다.
- 조건이 하나도 없을 때의 안내에 `직종으로 찾기` 바로연결을 더했다.

## 4. 인증과 환경변수

카카오가 제공하는 인증 수단은 스킬 설정의 **사용자 정의 헤더 값**뿐이다. 서명 검증이나 고정 IP 목록은 문서에 없다.

### 4.1 서버 동작

- 헤더 이름: `X-Skill-Token`
- 비교: `ActiveSupport::SecurityUtils.secure_compare`
- 토큰 출처(우선순위): 환경변수 `KAKAO_SKILL_TOKEN` → credentials `kakao.skill_token`
- 토큰이 비어 있을 때: 개발·테스트 환경은 인증 없이 허용하고, 그 외 환경은 모든 요청을 401로 거부한다(fail-closed). 즉 운영에 토큰 없이 배포하면 챗봇이 응답하지 않는다. 같은 이유로 **토큰 없는 호출의 401만으로는 토큰 설정이 성공했는지 알 수 없다.** 올바른 토큰으로 200을 확인해야 한다.

### 4.2 운영 설정 방식: credentials (확인 완료)

- `.kamal/secrets`의 `RAILS_MASTER_KEY`는 `config/credentials/production.key`를 읽는다. 따라서 운영 환경은 `config/credentials/production.yml.enc`를 복호화한다. (`master.key`와 `production.key`는 서로 다른 키이고, `production.yml.enc`는 `production.key`로만 복호화된다.)
- 운영 확인(2026-10-16 15:40 UTC): 토큰 없이 호출하면 401, 올바른 토큰으로 호출하면 200과 사례 JSON을 돌려준다. credentials 복호화가 서버에서 정상 동작한다.
- 같은 호출에서 확인한 것: 결과가 500건 이상인 무거운 검색의 `x-runtime`이 0.33초로 5초 제한에 여유가 있다.

토큰 설정 순서(기록):

1. 토큰 생성: `openssl rand -hex 32`
2. 편집: `bin/rails credentials:edit --environment production`
   ```yaml
   kakao:
     skill_token: <생성한 값>
   ```
3. `config/credentials/production.yml.enc`만 커밋한다(`production.key`는 gitignore).
4. `kamal deploy`. `deploy.yml`과 `.kamal/secrets`는 바꾸지 않는다.
5. 카카오 관리자센터에 같은 값을 입력한다(§5.2).

대안(환경변수): `config/deploy.yml`의 `env.secret`에 `KAKAO_SKILL_TOKEN`을 추가하고 `.kamal/secrets`에 `KAKAO_SKILL_TOKEN=$KAKAO_SKILL_TOKEN`을 추가한 뒤 배포 셸에서 값을 넘긴다. 긴급하게 값을 바꿔야 할 때는 환경변수가 credentials보다 우선하므로 임시로 쓸 수 있다.

### 4.3 토큰 교체

credentials 방식은 암호화 파일을 커밋하고 다시 배포해야 반영된다. 순서는 ① 새 값으로 credentials 수정·배포 ② 곧바로 카카오의 헤더값·테스트 헤더값 교체다. 두 단계 사이에 짧은 응답 불가 시간이 생기므로 운영 시간 외에 진행한다.

## 5. 카카오 관리자센터 설정

### 5.1 서버 사전 확인

배포 후 카카오 설정 전에 curl로 확인한다.

```bash
# 헤더 없이 → 401
curl -i -X POST https://t-13-67.xyz/webhooks/kakao \
  -H 'Content-Type: application/json' \
  -d '{"action":{"params":{"disease_name":"회전근개파열"}}}'

# 토큰을 넣으면 → 200 + JSON
curl -i -X POST https://t-13-67.xyz/webhooks/kakao \
  -H 'Content-Type: application/json' \
  -H 'X-Skill-Token: <토큰 값>' \
  -d '{"action":{"params":{"disease_name":"회전근개파열"}}}'
```

### 5.2 스킬 등록 (완료)

스킬 메뉴에서 생성 버튼을 눌러 입력한다. 필드는 `chatbot/skill_guide/make_skill.md` 기준이다.

| 필드 | 입력값 |
|---|---|
| 스킬명 | `판정 사례 검색` |
| URL | `https://t-13-67.xyz/webhooks/kakao` |
| Test URL | 배포 전 봇이 쓰는 주소(같은 서버면 같은 주소) |
| 헤더값 입력 | 이름 `X-Skill-Token`, 값 `<토큰>` |
| 테스트 헤더값 입력 | 이름 `X-Skill-Token`, 값 `<토큰>`(같은 값) |

- 배포 전 봇은 Test URL과 테스트 헤더값을, 배포 후에는 URL과 헤더값을 쓴다. **두 칸 모두 입력해야 한다.**
- 값 앞뒤에 공백이나 줄바꿈이 섞이면 401이 난다.
- 스킬은 공인 IP나 도메인만 쓸 수 있다. 로컬 서버는 연결할 수 없다.

### 5.3 스킬 테스트 (정상 확인함)

1. 파라미터 표에 `disease_name`, `job_name`, `work_factor`, `decision_type`을 추가한다. 키 이름은 서버가 읽는 이름과 같아야 한다.
2. **스킬 서버로 전송**을 누르고, 응답 미리보기와 응답 결과 로그를 확인한다.

| 증상 | 원인 후보 |
|---|---|
| 401 | 헤더 이름·값 불일치, 공백 혼입, 테스트 헤더값 누락 |
| 조건을 되묻는 응답 | 파라미터 키 이름 불일치 또는 값 없음 |
| 응답 없음 | 5초 타임아웃, 공인 도메인이 아님 |

### 5.4 블록 연결

블록 설정은 §7에 상세히 기록한다. 요점은 다음과 같다.

1. 사례 검색 블록의 **파라미터 설정**에서 등록한 스킬을 선택한다. 최신 버전이 자동 선택된다.
2. 응답 형식은 **스킬데이터로 사용**을 선택한다.
3. 블록의 파라미터 이름을 `disease_name`, `job_name`, `work_factor`, `decision_type`으로 맞춘다.
4. 스킬을 수정할 때는 **새 버전으로 저장**을 써서 이전 버전을 남긴다.

### 5.5 두 번째 스킬: 직종 검색

스킬 메뉴에서 하나 더 만든다. 헤더는 판정 사례 스킬과 같다.

| 필드 | 입력값 |
|---|---|
| 스킬명 | `직종 검색` |
| URL | `https://t-13-67.xyz/webhooks/kakao/jobs` |
| 헤더값 입력 / 테스트 헤더값 입력 | 이름 `X-Skill-Token`, 값 `<토큰>`(판정 사례 스킬과 같은 값) |

## 6. 엔티티

### 6.1 현황

| 엔티티 | 서버 매핑 | 측정 방식(`match`) | 대표 엔트리 | 동의어 | 사전이 덮는 사례 |
|---|---|---|---|---|---|
| `disease_name` | `LIKE` 부분 일치 | `like` | 54 | 107 | 80.2% (49,606 / 61,815) |
| `job_name` | `LIKE` 부분 일치 | `like` | 54 | 223 | 62.3% (38,485 / 61,815) |
| `work_factor` | `q` 전문 검색 | `fts` | 26 | 163 | 78.6% (48,594 / 61,815) |
| `decision_type` | enum 일치 | `exact` | 5 | 27 | 100% |
| `body_part` | `burden_body_part` 파이프 토큰 정확 일치(좌우 접두 확장) | `token` | 19 | 91 | 65.3% (40,384 / 61,815). 신체부위가 있는 사례(40,846건)의 **98.9%** |
| `skip_answer` | 서버 매핑 없음(단계별 흐름의 '모르겠어요' 답) | `static` | 1 | 11 | 건수 없음 |

- `job_name`은 직종이 비어 있는 사례(11.2%)를 빼면 직종이 있는 사례의 약 70%를 덮는다.
- 동의어가 가장 많은 행은 `disease_name` 8개, `job_name` 12개, `work_factor` 10개, `decision_type` 9개, `body_part` 15개, `skip_answer` 11개다.
- 데이터 기준은 로컬 개발 DB(판정서 61,815건)다. 운영 DB와 건수가 다를 수 있다.

### 6.2 사전과 도구

사전 파일 한 개가 엔티티 하나다. `config/chatbot/entities/<엔티티>.yml`:

```yaml
column: disease_name   # like/exact 방식의 검색 대상 컬럼
match: like            # like(기본) | exact | fts
min_hits: 5            # 합계 건수가 이보다 적은 개념은 CSV에서 제외
concepts:
  회전근개 파열:        # 개념명 = CSV의 '대표 엔트리' = 챗봇이 서버로 보내는 값
    db: [회전근개 파열, 회전근개파열, ...]   # DB에 실제로 나타나는 표기 변형(건수 측정)
    colloquial: [어깨 힘줄 파열, ...]        # 사용자가 말할 법한 표현
    exclude_synonyms: [...]                  # (선택) 건수 측정에는 쓰되 CSV 동의어에서는 뺄 표현
```

| `match` | 건수 측정 | `db`에 적는 것 |
|---|---|---|
| `like` | 공백을 무시한 부분 일치(`REPLACE(col,' ','') LIKE`) | DB 표기 변형 또는 핵심어 |
| `exact` | 컬럼 값 일치 | enum 값(동의어·중복 검사에서 제외) |
| `fts` | 서버 `DiseaseCase.main_search(q:)` 결과의 합집합 | `q`로 보낼 검색어 |
| `token` | 파이프로 이어진 `burden_body_part` 토큰을 서버 필터(`apply_main_filters`)로 센다. 좌우 접두 변형(`Chatbot::BodyPartExpansion`)까지 합쳐 센다 | 접두 없는 기본 토큰 |
| `static` | 건수 없음. 모든 개념을 사전 순서대로 그대로 출력 | `colloquial`에 동의어만(`db` 불필요) |

명령:

```bash
ENTITY=disease_name bin/rails chatbot:entities:build      # CSV 생성(docs/kakaotalk/entities/) + 건수 리포트
ENTITY=disease_name bin/rails chatbot:entities:discover   # 사전에 없는 용어를 건수 순으로 (LIMIT=, MIN= 조절)
bin/rails chatbot:entities:check                          # 모든 사전의 구조 + 엔티티 사이 중복 검증
```

- `build`는 **단순 LIKE**(대표 엔트리 하나만 서버로 보냈을 때)와 **변형 합집합**의 건수, 재현율, 사전이 덮는 사례 비율을 리포트로 보여 준다.
- 구조 검증: 한 표현이 두 개념에 중복되면 안 된다(대표↔동의어 포함, 공백 무시). `exclude_synonyms`의 표현은 그 개념에 실제로 있어야 하고 대표 엔트리일 수 없다. 글자 사이 공백은 연속 2칸 이상이면 안 된다. `db`가 비어 있으면 안 된다. 컬럼 이름과 엔티티 이름은 허용된 형태만 받는다(경로 이탈·SQL 문자 거부).
- `discover`는 `match: like` 사전만 지원한다(다른 방식은 안내 후 종료). 복합 값을 `/`로 쪼개고 좌우 구분(우측·좌측)과 번호(제4-5번)를 떼서 센다. "우울증", "좌골신경통"은 손상하지 않고, "요추", "견관절" 같은 신체 부위만 남은 조각은 뺀다.
- **엔티티 사이 중복 검사**: 같은 표현(공백 무시)이 서로 다른 엔티티의 대표 엔트리·동의어에 걸치면 `check`와 테스트가 실패한다. 카카오 문서가 동의어 중복 등록 시 인식이 어렵다고 경고하기 때문이다. 한쪽 엔티티에서 `exclude_synonyms`로 빼서 해결한다(§6.3 기록).
- 테스트: 건수 계산(공백 무시, 합집합), 정렬, 동의어 병합·중복 제거, 구조 검증 실패, 엔티티 사이 중복, `exclude_synonyms`, CSV 형식(헤더 없음·행 폭 맞춤·쉼표 인용), 커밋된 사전·CSV 검증, `exact`·`fts` 방식, 그리고 **`decision_type` 대표 엔트리가 서버 `KakaoRequestAdapter`의 변환표와 일치하는지**(어긋나면 챗봇이 판정 필터를 조용히 버린다).

### 6.3 CSV 형식과 업로드

카카오 샘플(관리자센터에서 내려받는 파일) 형식을 따른다.

```
가구거리,가구촌,가구마을,,,,
예식장,웨딩홀,결혼식장,,,,
웨딩스튜디오,웨딩촬영스튜디오,웨딩촬영장,결혼사진스튜디오,,,
```

- **헤더 행이 없다.** 첫 열이 대표 엔트리, 이후 **열마다 동의어 하나**다.
- 모든 행의 폭이 같도록 모자란 칸은 빈 칸으로 채운다. 폭은 동의어가 가장 많은 행이 정한다.
- UTF-8, BOM 없음.
- **기록(실수와 수정):** 처음에는 샘플 없이 `대표 엔트리,동의어` 두 열에 동의어를 쉼표로 묶어 만들었다. 카카오가 이를 동의어 하나로 읽어 묶음 전체가 한 동의어로 등록됐다. 카카오 쪽 문제가 아니라 형식을 추측한 탓이었다. 샘플을 받아 위 형식으로 고쳤다.
- 샘플의 동의어는 최대 6개였다. 이 사전은 그보다 많은 행이 있다(§6.1). 카카오에 열 수 제한이 있는지는 문서에 없다.
- **기록(엔티티 사이 중복):** 업로드 중 `work_factor.csv`가 직접 수정됐다. 사전에서 새로 만든 결과와 비교하니 `상하차`, `적재`, `짐 나르기`(→ `짐을 나르기`로 바꿈), `석면` 네 표현이 달랐고, 이는 엔티티 사이에 겹치는 표현 4개와 정확히 일치했다(`상하차`·`적재`·`짐 나르기`는 `job_name`의 물류 노동자와, `석면`은 `disease_name`의 대표 엔트리와 겹침). 당시 검사는 한 엔티티 안의 중복만 봐서 놓쳤다.
  - 조치: 수정된 CSV를 그대로 유지하고, 같은 결정을 사전에 옮겼다(`물건 운반`·`석면 노출`의 `exclude_synonyms`). 사전에서 다시 만든 CSV가 수정본과 **바이트 단위로 같음**을 확인했다. 엔티티 사이 중복 검사를 `check`와 테스트에 추가했다.
  - 교훈: CSV를 직접 고치면 사전과 어긋난다. 고칠 때는 사전을 먼저 고치고 `build`로 다시 만든다(어긋나면 테스트가 실패한다).

### 6.4 분석 결과

**전체:** 판정서 61,815건.

**`decision_type`**
- `result`는 4종뿐이고 비어 있는 값이 없다. 인정 49.1%, 불인정 38.2%, 일부인정 11.0%, 변경인정 1.7%.
- "인정"은 "불인정"·"일부인정"·"변경인정"의 일부 글자다. 카카오가 가장 긴 표현을 우선하는지 확인하지 못했다(§9 T5·T6).
- '각하'는 본안 판단 없이 청구를 물리치는 것이라 '불인정'과 같지 않아 동의어에 넣지 않았다.

**`disease_name`**
- 서로 다른 질병명이 42,791개이고 58%가 `/`로 이어진 복합 값이다. 띄어쓰기도 제각각이다(예: "회전근개 파열" / "회전근개파열").
- 같은 질병도 표기가 갈린다: 충돌/충격증후군, 외측상과염/외상과염, 반월상 연골/연골판/반달연골.
- 사전 보강 과정에서 `discover`로 요추·경추 염좌, 윤활막염, 점액낭염, 삼각섬유연골복합체 파열, 편마비, 고혈압, 폐렴, 그리고 극상건 파열·반월판·COPD 표기를 찾아 넣었다. 덮는 사례가 75.7%에서 80.2%로 올랐다.
- "추간판돌출증"(91건)은 탈출증과 의학적으로 다를 수 있어 합치지 않았다.

**`job_name`**
- 직종이 채워진 사례 54,867건(88.8%), 서로 다른 값 25,077개, 길이 중앙값 6자. 상위 100개 핵심어가 40.3%만 덮는 긴 꼬리 분포다.
- 서버가 부분 일치로 검색하므로 "조리", "용접" 같은 짧은 핵심어가 잘 맞는다(조리는 조리원·조리사·급식조리·주방조리를 포함).
- "건설 및 광업 단순 종사원"(331건) 같은 직업분류 항목명은 사용자가 말하는 표현이 아니라 넣지 않았다.

**`work_factor`**
- 전문 검색은 **단어 전체**가 일치해야 걸린다. "반복"(10,180건), "반복적인"(9,644건), "반복적으로"(2,582건)가 서로 다른 단어라 변형을 따로 적었다. 띄어쓰기로 구분한 검색어는 모든 단어가 있어야 한다(AND).
- 전문 검색 대상은 `job_name`, `job_description`, `main_reasoning`, `other_harmful_factors`, `aggravating_factors`이며 **자세(`bad_posture`) 컬럼은 대상이 아니다.**
- 전문 검색은 요인이 '언급'된 사례를 찾는다. 측정: "중량물" 언급 17,215건 중 97.8%가 구조화 컬럼 `heavy_lifting='Y'`와 일치했고 부정 표현 동반은 16건이었다. 다른 요인은 대조할 컬럼이 없어 검증하지 못했다.
- 일반적인 형용사로 묶은 항목("과도한", "무리한", "강한")은 정밀도가 낮아 뺐고, 흡연은 업무 요인이 아니라 뺐다.
- 구조화 컬럼이 있는 요인(중량물 취급 `heavy_lifting`, 부담 부위 `burden_body_part`)은 후속으로 구조화 필터를 쓰면 더 정확하다.

### 6.5 알려진 한계: 서버 검색의 재현율

서버가 대표 엔트리 **하나만** 검색하므로 재현율이 낮다. 사전의 `db` 변형을 합친 건수와 비교하면 다음과 같다.

| 엔티티 | 대표 엔트리 | 대표어만 검색 | 변형 합집합 |
|---|---|---|---|
| `disease_name` | 어깨 충돌증후군 | 532건 | 6,193건 |
| `disease_name` | 외측상과염 | 1,058건 | 3,763건 |
| `disease_name` | 퇴행성 관절염 | 588건 | 2,075건 |
| `disease_name` | 소음성 난청 | 0건 | 79건 |
| `job_name` | 환경미화원 | 907건 | 2,407건 |
| `job_name` | 버스기사 | 12건 | 673건 |
| `job_name` | 물류 노동자 | 0건 | 1,357건 |
| `work_factor` | 반복 동작 | 2,421건 | 19,450건 |
| `work_factor` | 좁은 작업공간 | 2건 | 3,309건 |
| `work_factor` | 몸통 비틀림 | 1건 | 1,469건 |

- 원인: ① 공백을 무시하지 않는다(예: "회전근개파열"은 6,090건 중 969건만 걸린다). ② 한 개념의 여러 표기를 `OR`로 묶지 않는다. ③ `work_factor`는 다단어 대표 엔트리가 모든 단어를 요구하는 AND 검색이 된다.
- **카카오 쪽 블록 문제가 아니므로 봇 테스트에서 결과가 적게 나와도 놀라지 않는다.** 서버 검색 확장(§13)으로 개선한다. 사전의 `db` 목록이 그 매핑 자료다.

### 6.6 업로드 후 확인

- [ ] 동의어가 개별로 나뉘어 등록됐는가(예: `불인정`에 `불승인`, `기각`, `거절`이 따로 보임)
- [ ] 열 수 제한 때문에 동의어가 잘리지 않았는가(`job_name` 12개, `work_factor` 10개, `decision_type` 9개, `disease_name` 8개)
- [ ] 대표 엔트리 개수: `disease_name` 54, `job_name` 54, `work_factor` 26, `decision_type` 5, `body_part` 19, `skip_answer` 1
- [ ] **"불인정 사례"에서 `decision_type`이 `불인정`으로 추출되는가**(`인정`으로 잡히면 판정이 거꾸로 검색됨)
- [ ] 띄어쓰기 변형이 인식되는가. 사전은 띄어쓰기만 다른 동의어를 하나만 남긴다(예: "일부 인정"은 "일부인정"과 같다고 보고 제외). 카카오가 이를 같은 표현으로 인식하지 않으면 변형을 되살려야 한다.
- [ ] `body_part`·`skip_answer`(단계별 사례 찾기용)가 개별 동의어로 나뉘어 올라갔는가(`body_part` 최대 15개, `skip_answer` 11개)
- [x] 엔티티 사이 중복 표현이 없는가(4건 발견·해결, `check`가 이후 재발을 막는다)
- [ ] 이전(잘못된 형식)에 올린 항목이 남아 있지 않은가. 남아 있으면 해당 엔티티를 지우고 다시 올린다.
- [ ] 직종·요인 묶음과 의료·노동 용어는 작성자의 판단이므로 전문가 검토를 받는다.

### 6.7 신체부위 확장과 공유 필터 변경

**사전과 확장**
- `body_part.yml`은 `burden_body_part`(파이프로 이어진 값)의 토큰을 개념별로 묶는다. 좌우 구분을 뗀 서로 다른 토큰이 849개이고 상위 15개가 신체부위가 있는 사례의 95.6%를 덮으며, 사전 19개 개념은 **98.9%**(40,384 / 40,846)를 덮는다. 신체부위가 없는 사례(33.9%)는 대부분 뇌출혈 같은 질병이라 이 질문에 해당 없다.
- 서버 필터가 토큰을 **정확히** 일치시켜서 `어깨`만 찾으면 `우측 어깨`를 놓친다. 그래서 `Chatbot::BodyPartExpansion`이 사전 대표 → db 토큰들 → **좌우 접두 변형**(`우측 `/`좌측 `/`양측 `)으로 확장한다. 사전에 없는 값은 그 값 자체(와 접두 변형)로 찾는다.
- 접두는 4가지(없음·우측·좌측·양측)만 쓴다. 개발 DB 토큰 82,938개 중 이 4가지가 99.38%이고 나머지(왼쪽·오른쪽·양쪽·양·우·좌)는 합쳐 0.62%다. 값이 늘수록 검색이 느려져서 나머지는 일부러 뺐다(건수 약 0.6% 손실).

**공유 필터 변경과 성능**
- 처음 구현(접두 10가지)은 조합에 따라 응답이 2.4~2.9초까지 올랐다. 카카오 응답 제한(5초)의 절반을 넘는 값이다. 원인은 `apply_main_filters`의 신체부위 조건이 값마다 `LIKE`를 4번(정확·앞·뒤·중간) 쓰고, 한 개념이 토큰×접두로 수십 개 값이 되어 행마다 `LIKE`를 수백 번 평가한 것이다.
- `apply_main_filters`의 신체부위 조건을 컬럼 양끝에 파이프를 붙인 `('|' || burden_body_part || '|') LIKE '%|값|%'` **하나**로 바꿨다. 의미는 같고(정확히 일치·맨앞·맨뒤·중간을 모두 잡음) 이 필터는 웹 검색·MCP도 쓰는 공유 코드다.
  - 검증: 개발 DB에서 상위 토큰·무작위 토큰·묶음 55개로 변경 전후 결과 id가 **모두 같음**(불일치 0건). 웹 검색 테스트 통과.
- 결과(개발 노트북, 처음 호출 기준): 신체부위+판정 2,926ms → 84ms, 직종+신체부위+판정 2,380ms → 144ms, 신체부위+판정+작업 요인(전문 검색 포함) 798ms. 나머지 조합은 대부분 150ms 이하다. 운영 서버는 더 느릴 수 있어 §12.2에서 다시 잰다.

### 6.8 작업 요인 검색의 시간 초과와 전문 검색 필터화

**증상:** 단계별 사례 찾기의 마지막 블록(`판정 사례 검색` 스킬 호출)에서 스킬 시간 초과(5초)가 났다. 운영 로그의 `duration_ms`와 입력 조건은 확인하지 못했다.

**원인(개발 DB 61,815건에서 재현):** 작업 요인은 `q`로 전문 검색(FTS)한다. `main_search`는 FTS 테이블을 JOIN하고 `bm25`로 정렬하는데, 이 정렬은 매칭된 행 전체에 점수를 매긴 뒤 상위 10건을 고른다. 판정 같은 구조 필터가 넓으면(작업 요인 + 판정) 매칭 행이 수만 건이라 오래 걸린다. 앞 질문을 "모르겠어요"로 넘기고 작업 요인과 판정만 남는 조합이 가장 나쁘다. 처음 실행은 DB 페이지 캐시가 비어 더 느리다(같은 쿼리 재실행은 1ms).

| 조합 | 수정 전(목록 쿼리) | 수정 후 |
|---|---|---|
| 중량물 취급 + 인정 | 4,208ms | 53ms |
| 부적절한 자세 + 인정 | 2,293ms | 10ms |
| 반복 동작 + 불인정 | 912ms | 2ms(서브쿼리 직접 측정) |
| 직종 + 신체부위 + 질병 + 작업 + 판정(5개 모두) | 3,907ms(첫 실행) | 6ms |

**수정(`8cf2ab3`, `b94a7f5`):**
- `main_search`에 `fts_as_filter` 옵션을 추가했다. 주면 FTS를 `disease_cases.id IN (SELECT rowid ... MATCH ?)` **서브쿼리 필터**로만 쓰고 `year` 내림차순(최신순)으로 정렬한다. `Chatbot::CaseSearch`만 이 옵션을 준다. 웹 검색 화면은 옵션을 주지 않아 기존 관련도(`bm25`) 순서 그대로다.
- FTS에 일치가 없을 때 직종 부분 일치로 넘어가는 폴백은 그대로다(테스트로 고정).
- **바뀐 점:** 작업 요인을 입력한 챗봇 검색은 관련도 순이 아니라 **최신순**으로 나온다.

**남은 것:** 운영 서버에서 같은 조합으로 재시험한다. 그래도 시간 초과가 나면 운영 로그의 `duration_ms`를 보고 ① 서버 기동 시 FTS·주요 인덱스 예열 ② 처리 시간 상한(약 4초에서 중단하고 "조건을 하나 더 알려 달라" 안내)을 추가한다. 둘 다 아직 구현하지 않았다.

## 7. 블록 구성

관리자센터는 **시나리오 → 블록** 구조다. 설명은 `chatbot/tutorial/make_chatbot/tutorial_1~3.md`, `main_notions/block.md`, `setting_parameter.md`, `context.md` 기준이며, 실제 화면은 확인하지 못했다. 특히 **그룹 파라미터의 되묻기 설정 위치**는 문서에 없어 화면에서 확인해야 한다.

### 7.1 시나리오와 블록

| 시나리오 | 블록 |
|---|---|
| 처음으로·도움말 | 웰컴(기본), 처음으로, 도움말, 폴백(기본) |
| 판정 사례 검색 | 판정 사례 찾기, 다른 사례 보기, 검색 조건 바꾸기, 승인 가능성 문의 |
| 단계별 사례 찾기 | 시작, 답변1~5 (§7.6) |
| 산재 신청 안내 | 후속 작업(`GUIDE`) |

```
[웰컴/처음으로] ──▶ 안내 + 바로연결(판정 사례 찾기 / 도움말)

사용자 발화 ──▶ [판정 사례 찾기] ──스킬──▶ 사례 목록(10건)
                  파라미터 4개              ├ 다른 사례 보기 ──▶ [다른 사례 보기] ──스킬──▶ 다음 10건
                  (3개는 그룹)              ├ 조건 바꾸기 ────▶ [검색 조건 바꾸기]
                                            └ 처음으로 ───────▶ [처음으로]

이해 못 한 입력 ──▶ [폴백] ──▶ 도움말 + 처음으로
"산재 될까요?" ──▶ [승인 가능성 문의] ──▶ 사례 검색 안내
```

### 7.2 작업 순서

튜토리얼도 이동할 블록부터 먼저 만든다. 버튼에 블록을 연결하려면 대상 블록이 있어야 해서 순서가 중요하다.

1. **시나리오 설정**: 되묻기 최대 횟수 2회, 최대 시간 30분(범위 10~120분), 한도 초과 시 안내 메시지(§7.3 ④).
2. 시나리오 2개 생성.
3. **빈 블록의 이름부터 전부 만든다**(처음으로, 도움말, 판정 사례 찾기, 다른 사례 보기, 검색 조건 바꾸기, 승인 가능성 문의).
4. 웰컴 → 처음으로 → 도움말 → 폴백 순으로 응답을 채운다.
5. 판정 사례 찾기 블록(발화, 파라미터, 되묻기, 스킬).
6. 나머지 블록 입력 후 봇 테스트(§9). 봇 테스트는 카카오톡 채널 없이도 된다(Ctrl+E).
7. 실제 카카오톡 확인은 개발 채널 연결 후(튜토리얼 1단계의 채널 연결).

### 7.3 블록별 설정

#### ① 웰컴 블록 (기본 블록)

- **"미사용"이 기본값**이라 사용 중으로 바꿔야 한다. 최초 1회만 나간다.
- 응답은 최대 3개. 텍스트형은 버튼이 있으면 400자까지(없으면 1,000자, 여러 개일 때는 128자).
- 웰컴은 야간에도 발송될 수 있어 **광고성 내용을 넣으면 안 된다.**

```
안녕하세요, 산재상담실입니다.
업무상 질병 판정서에서 비슷한 사례를 찾아 드려요.

※ 검색 결과는 참고 자료이며, 개인의 산재 승인 가능성을 뜻하지 않습니다.
※ 이름, 주민등록번호, 전화번호 같은 개인정보는 입력하지 마세요.
```

바로연결: `판정 사례 찾기`, `도움말`. 산재 신청 안내 블록이 아직 없어 막다른 길이 되지 않도록 그 버튼은 `GUIDE`를 만들 때 추가한다.

#### ② 처음으로 블록

- 웰컴이 한 번만 나가므로, 같은 내용의 **일반 블록**을 만들어 서버가 보내는 `처음으로` 버튼의 도착점으로 쓴다.
- 발화 패턴은 정확히 `처음으로` 하나.
- 튜토리얼의 카드형은 이미지가 필요하다. 이미지 없이 하려면 **텍스트형 + 바로연결**을 쓴다.

#### ③ 도움말 블록

발화: `도움말`, `사용법`, `어떻게 써요`.

```
이렇게 말씀해 보세요.
• 회전근개파열 사례 찾아줘
• 용접 일 하는데 어깨가 아파요
• 허리디스크 불인정 사례 보여줘

질병명, 직종, 작업 내용 중 하나만 있어도 찾아 드려요.
```

바로연결: `판정 사례 찾기`, `처음으로`.

#### ④ 판정 사례 찾기 (핵심)

**발화 패턴**
- 예상 문장을 입력하고 엔티티 단어를 드래그해 태깅한다. 밑줄이 없는 단어도 직접 태깅할 수 있다. 목록은 §8.
- **어순이 바뀌면 다른 패턴으로 인식**되므로 어순별로 따로 등록한다.
- **엔티티 없는 발화 `판정 사례 찾기`도 등록한다.** 웰컴·도움말의 `판정 사례 찾기` 버튼이 이 문장을 보내고, 조건이 비어 있으니 곧바로 되묻기로 이어진다. 별도 시작 블록이 필요 없다.

**파라미터**

| 이름 | 엔티티 | 값 | 필수 |
|---|---|---|---|
| `disease_name` | `disease_name` | `$disease_name` | 그룹 |
| `body_part` | `body_part` | `$body_part` | 그룹 |
| `job_name` | `job_name` | `$job_name` | 그룹 |
| `work_factor` | `work_factor` | `$work_factor` | 그룹 |
| `decision_type` | `decision_type` | `$decision_type` | 아니오 |

- 이름은 서버가 읽는 `action.params` 키와 정확히 같아야 한다.
- 네 개(`disease_name`, `body_part`, `job_name`, `work_factor`)를 **그룹 파라미터**로 묶는다. 그룹은 필수가 되고 안의 값이 **하나라도 채워지면 통과**한다. 모두 비어 있을 때만 되묻기가 나간다.
- `decision_type`은 필수가 아니다. 비면 서버가 판정 결과로 거르지 않는다.

**되묻기 질문**(최대 3개, 허용 횟수 안에서 무작위 출력)

```
1) 어떤 질병이나 직종, 작업이 궁금하세요? 예) 회전근개파열, 용접, 중량물 취급
2) 찾고 싶은 사례의 질병명이나 직종을 알려주세요. 예) 허리디스크, 조리원
3) 질병명, 직종, 작업 내용 중 하나만 알려주셔도 찾아 드려요.
```

- 되묻기 **바로연결 응답**에 자주 쓰는 값을 넣어 정확한 답을 유도한다. 예: `회전근개 파열`, `추간판 탈출증`, `손목터널증후군`, `뇌경색`
- 횟수 초과 안내(시나리오 설정): `조건을 이해하지 못했어요. 질병명이나 직종을 짧게 입력해 주세요.` + `처음으로`

**스킬 연결**: 파라미터 설정에서 스킬을 선택하고, 응답 형식은 **스킬데이터로 사용**을 고른다.

#### ⑤ 다른 사례 보기

- 발화 패턴은 서버 버튼의 `messageText`와 **정확히 같은 `다른 사례 보기`**.
- **필수 파라미터를 두지 않는다.** 바로연결은 엔티티를 다시 추출하지 않으므로, 필수 파라미터가 있으면 되묻기가 나가 흐름이 끊긴다. 이전 조건은 서버가 `clientExtra`로 받는다.
- 스킬을 연결하고 **스킬데이터로 사용**을 고른다.

#### ⑥ 검색 조건 바꾸기

- 발화 `검색 조건 바꾸기`. 스킬 없는 정적 블록.
- 서버는 이 버튼을 일반 검색과 구분하지 않아서, 스킬에 연결하면 같은 검색이 다시 실행된다. 그래서 정적 블록으로 둔다.
- 응답: `바꾸고 싶은 조건을 말씀해 주세요. 예) 허리디스크 불인정 사례`
- **이전 조건은 유지되지 않는다.** 유지하려면 컨텍스트(출력·입력 컨텍스트, 스킬 요청의 `contexts`)와 서버 수정이 필요하다. 별도 작업(§13, 결정 §14).

#### ⑦ 승인 가능성 문의

기획서의 안전 기준(승인 확률 단정 금지)을 위한 블록이다.

- 발화: `산재 될까요`, `승인될 수 있나요`, `인정받을 수 있어요`, `제 경우 가능한가요`
- 응답:
```
개인의 산재 승인 여부는 판단해 드릴 수 없어요.
대신 비슷한 업무와 질병의 판정 사례를 찾아 참고하실 수 있어요.
```
- 바로연결: `판정 사례 찾기`, `처음으로`

#### ⑧ 폴백 블록 (기본 블록)

전송 타입을 **랜덤형**으로 두고 문구 3개를 등록한다.

```
1) 죄송해요, 무슨 말씀인지 잘 모르겠어요. 질병명이나 직종으로 말씀해 주시겠어요?
2) 아직 이해하지 못했어요. '판정 사례 찾기'를 눌러 시작해 보세요.
3) 승인 여부는 판단해 드릴 수 없고, 비슷한 판정 사례를 찾아 드려요.
```

문구 아래에 바로연결 `판정 사례 찾기`, `처음으로`, `도움말`을 붙인다. 튜토리얼도 폴백에 홈 메뉴를 같이 두는 것을 권한다.

### 7.4 서버가 보내는 문장과 블록 발화(어긋나면 버튼이 폴백으로 간다)

| 서버가 보내는 `messageText` | 받는 블록 | 발화 패턴 |
|---|---|---|
| `다른 사례 보기` | ⑤ | 정확히 같은 문장 |
| `검색 조건 바꾸기` | ⑥ | 정확히 같은 문장 |
| `처음으로` | ② | 정확히 같은 문장 |

문장을 바꾸면 `Chatbot::KakaoResponseBuilder`의 `HOME_MESSAGE`, `REFINE_MESSAGE`, `MORE_MESSAGE` 상수도 함께 바꾼다.

### 7.5 위험과 확인할 것

1. **"인정"이 "불인정"의 일부 글자다.** "불인정 사례"에서 `decision_type`이 `불인정`으로 잡혀야 한다. 반대로 잡히면 판정이 거꾸로 검색된다.
2. **한 문장에 같은 엔티티가 둘 이상**(예: "허리디스크랑 회전근개") 나올 때 어떻게 추출되는지 문서에 없다. 테스트로 확인한다.
3. **`work_factor`는 사전에 있는 표현만 잡힌다.** 사전에 없는 표현만 말하면 그룹 파라미터가 비어 되묻기가 나간다.
4. **서버 재현율이 낮다**(§6.5). 결과가 적어도 블록 문제가 아니다.
5. 개발 중이라 Rails 기본 `Parameters:` 로그에 발화 원문이 남는다. 테스트에 실제 개인정보를 넣지 않는다(§10).
6. **발화는 모든 블록에서 서로 달라야 한다(관리자센터에서 확인함).** 같은 발화를 다른 블록에 넣으면 입력 컨텍스트가 달라도 **중복 오류**가 난다. 그래서 "같은 패턴을 여러 블록에 두고 입력 컨텍스트로 구분한다"는 설계는 쓸 수 없다. `{job_name}`·`{skip}` 같은 단독 패턴은 **한 블록만** 가질 수 있고, 여러 단계가 같은 의미를 가져야 하면(예: 건너뛰기) 단계 이름을 붙여 블록마다 다른 문장으로 만든다(§7.6). 새 발화를 넣을 때마다 다른 블록과 겹치는지 확인한다.

### 7.6 단계별 사례 찾기 시나리오

조건을 한 문장으로 말하기 어려운 사용자를 위한 **별도 시나리오**다. 질문 5개를 하나씩 던지고, 답하거나 "모르겠어요"로 넘기면서 값을 모은 뒤 **마지막에 스킬을 한 번만** 호출한다. `판정 사례 찾기`(§7.3 ④)와는 따로 둔다.

**질문 순서(확정):** 직종 → 신체부위 → 질병 → 작업 요인 → 판정 결과. 블록이 대칭이라 순서는 바꾸기 쉽다.

```
[시작]   소개 + Q1(직종)                         out: wiz1
[답변1]  in wiz1  job_name     | skip   → Q2(신체부위)   out: wiz2  (job_name)
[답변2]  in wiz2  body_part    | skip   → Q3(질병)       out: wiz3  (+body_part)
[답변3]  in wiz3  disease_name | skip   → Q4(작업 요인)   out: wiz4  (+disease_name)
[답변4]  in wiz4  work_factor  | skip   → Q5(판정 결과)   out: wiz5  (+work_factor)
[답변5]  in wiz5  decision_type| skip   → 스킬 호출(5개 값 전부) → 사례 목록(listCard 10건)
```

**설계 이유**
- **각 답변 블록의 입력 컨텍스트는 바로 앞 단계 하나뿐**이다. 앞 단계 값은 파라미터 값 칸에 `#wizN.<파라미터명>`으로 다시 받아 자기 출력 컨텍스트에 **누적해서 내보낸다.** 다중 입력 컨텍스트의 의미(AND/OR)가 문서에 없어서 이 불확실성을 피하려는 구성이다.
- 컨텍스트는 수명 3블록(오타로 폴백이 한두 번 끼어도 유지), 유효시간 30분(기획서의 되묻기 30분과 일치)이다. 문서상 수명 선택지는 0/1/3/5/10, 유효시간은 1/3/5/10/15/30/60분이다.
- 단계마다 파라미터를 **그룹 파라미터** `[그 단계 엔티티, skip]`으로 묶는다. 하나만 채워져도 통과하므로 값을 말하든 "모르겠어요"를 말하든 다음 단계로 간다. 되묻기·횟수 초과로 흐름이 끊기지 않는다.
- `skip_answer` 엔티티(대표 `모름`)를 **모든 단계가 공유**한다. 엔티티마다 모름 값을 따로 두면 같은 동의어가 엔티티 사이에서 겹쳐 `check`가 막는다. 판정 결과의 `전체` 동의어(모두·전부·상관없음·아무거나)와 겹치지 않게 skip 동의어에서 뺐다.
- 서버는 `모름`이나 `#wiz…`처럼 해석되지 않은 참조를 조건 없음으로 버린다(§3.1). 다섯 값이 모두 비면 "하나 이상 알려 달라"는 안내와 `단계별로 찾기` 버튼을 보낸다.
- 최종 호출은 기존 서버 계약을 그대로 쓰므로 `다른 사례 보기`는 신체부위를 포함한 5개 조건을 `clientExtra`로 이어 간다.

**블록**

| 블록 | 입력 컨텍스트 | 파라미터(그룹) | 출력 컨텍스트 | 응답 |
|---|---|---|---|---|
| 시작 | 없음 | 없음 | `wiz1` | 소개 + Q1 + 바로연결 |
| 답변1 | `wiz1` | `job_name` \| `skip` | `wiz2`(job_name) | Q2 + 바로연결 |
| 답변2 | `wiz2` | `body_part` \| `skip`, `job_name=#wiz2.job_name` | `wiz3`(+body_part) | Q3 |
| 답변3 | `wiz3` | `disease_name` \| `skip` + 앞 값 `#wiz3.*` | `wiz4` | Q4 |
| 답변4 | `wiz4` | `work_factor` \| `skip` + 앞 값 `#wiz4.*` | `wiz5` | Q5 |
| 답변5 | `wiz5` | `decision_type` \| `skip` + 앞 값 `#wiz5.*` | 없음 | **스킬 호출**(스킬데이터로 사용) |

**발화·문구**
- 시작 발화: `단계별로 찾기`, `하나씩 물어봐 줘`, `차근차근 찾고 싶어요`. 답변 블록 발화는 그 단계 엔티티 단어를 태깅한 짧은 문장이다. **발화는 블록 사이에서 고유해야 한다(§7.5 6).**
  - 값 발화(`{job_name}`, `{body_part}` …)는 그 단계 블록만 가진다. `판정 사례 찾기`·`직종 입력` 등 다른 블록은 같은 단독 패턴을 쓰지 않고 문장 형태(예: `{job_name} 산재 사례`)로 바꾼다.
  - **건너뛰기 발화는 단계 이름을 붙여 블록마다 다르게 한다(제안, 시험 전):** 답변1 `직종 {skip}`, 답변2 `부위 {skip}`, 답변3 `병명 {skip}`, 답변4 `작업 {skip}`, 답변5 `판정 {skip}`. `모르겠어요` 바로연결은 라벨을 `모르겠어요`로 두고 messageText를 `직종 모르겠어요`처럼 단계마다 다르게 한다. 공통 `{skip}` 발화는 중복 오류로 넣을 수 없고, 발화가 없으면 `모르겠어요`가 폴백으로 간다.
  - **관리자센터에 실제로 등록한 발화 목록은 기록하지 못했다.** 재설정한 내용을 이 항목에 맞춰 적을 것.
- 웰컴·도움말·폴백·`검색 조건 바꾸기`에 `단계별로 찾기` 바로연결을 추가한다. 서버도 조건이 없을 때 이 버튼을 보낸다.
- 질문 예: `어떤 일을 하시나요? 예) 용접, 조리, 청소. 모르면 '모르겠어요'를 눌러 주세요.` 바로연결은 `모르겠어요`(messageText 동일) + 자주 찾는 값 3~4개 + `처음부터`, `그만두기`(`처음으로`).
  - 직종: 용접공 · 조리원 · 환경미화원 / 신체부위: 어깨 · 허리 · 무릎 · 손목 / 질병: 회전근개 파열 · 추간판 탈출증 · 손목터널증후군 / 작업: 반복 동작 · 중량물 취급 / 판정: 인정 · 불인정 · 전체
  - 라벨 14자 이내, 바로연결 10개 이하.
- 단계 도중 이해 못 한 입력은 전역 폴백으로 간다. 폴백 문구에 "모르겠어요로 넘어가거나 처음부터 다시 시작할 수 있어요"를 넣어 대응한다. 개인정보 입력 금지 안내는 시작 블록에 둔다.
- 마지막에 조건을 확인·수정하는 단계는 컨텍스트 구조상 복잡해져 넣지 않았다. 결과 요약 텍스트에 적용된 조건이 보이고 `검색 조건 바꾸기`·`단계별로 찾기`로 다시 시작할 수 있다.

**먼저 할 것: 컨텍스트 흐름 검증(Step 0).** 문서로 확정할 수 없는 동작이 많아, 전체를 만들기 전에 시작·답변1·답변2 블록만 만들어 봇 테스트한다.
1. ~~입력 컨텍스트가 있는 답변 블록이 같은 단어에 반응하는 일반 블록(`판정 사례 찾기`)보다 우선하는가.~~ 같은 발화를 여러 블록에 등록할 수 없어서(§7.5 6) **더 이상 확인할 필요가 없는 항목**이다. 발화를 블록마다 고유하게 둔다.
2. `#wiz2.job_name` 참조가 값이 있을 때 정상 전달되고, **값이 없을 때(모름)** 빈 값인지 문자열 그대로인지.
3. 엔티티 단어 하나만 입력한 발화(`{job_name}` 단독 패턴)가 블록에 등록·인식되는가.
4. 출력 컨텍스트 수명 3·유효시간 30분이 의도대로 소비·만료되는가(오타 입력이 폴백을 거치는 경우 포함).
5. 그룹 파라미터 `[엔티티, skip]`이 둘 중 하나만 채워져도 통과하는가.

결과가 맞지 않으면 대안으로 각 단계 블록이 얇은 스킬 엔드포인트를 불러 서버가 컨텍스트 `params`에 값을 누적하는 방식이 있다. 다만 요청이 단계마다 생겨 "마지막에 한 번 요청"에서 벗어나므로 Step 0 결과를 보고 다시 정한다.

**관리자센터 시험 결과와 미해결 항목(2026-10-19 기준, 진행 중)**

| 순서 | 증상 | 원인·조치 | 상태 |
|---|---|---|---|
| 1 | 답변1(직종) 발화가 `직종 입력` 블록(§7.7)과 겹친다는 표시. 이후 `{skip}`을 단계 블록에 넣어도 **중복 오류** | 두 블록이 `{job_name}` 패턴을 쓰고 입력 컨텍스트(`wiz1`·`job_kw`)로 구분하는 설계였으나, 관리자센터는 컨텍스트와 무관하게 중복을 막는다(§7.5 6). 전체 블록의 발화가 겹치지 않도록 관리자센터에서 재설정했다. **재설정한 발화 목록은 기록하지 못했다** | 해결(재설정함) |
| 2 | `단계별로 찾기` 다음 `용접` 입력이 **폴백 블록**으로 감 | 우선순위 문제가 아니라 답변1이 후보에도 오르지 못한 것이다. 위 1의 중복 때문에 발화가 저장되지 않았을 가능성이 있다. 확인 순서: ① 답변1에 발화가 저장됐는가 ② `단계별로 찾기` 직후 컨텍스트에 `wiz1`이 있는가 ③ 인풋 컨텍스트 이름 ④ `용접공이요`·`용접 일해요` 같은 문장형은 되는가 ⑤ `용접`이 엔티티에 있는가 | 결과 미확인 |
| 3 | 마지막 블록 스킬 **시간 초과** | §6.8 | 서버 수정 완료, 운영 재시험 필요 |
| 4 | `모르겠어요`를 선택하면 **다음 단계로 넘어가지 못함** | **원인 확인:** 중복 오류 때문에 `{skip}` 발화를 답변 블록에서 삭제했고, 그러면 `모르겠어요`는 어떤 발화와도 맞지 않아 폴백으로 간다(그룹 파라미터는 블록이 선택된 뒤에 쓰이는 설정이라 발화가 없으면 소용없다). `skip_answer.csv`에는 `모르겠어요`가 있어 서버·CSV 문제는 아니다. **조치(제안):** 단계 이름을 붙인 고유 발화 `직종 {skip}`·`부위 {skip}`·`병명 {skip}`·`작업 {skip}`·`판정 {skip}`와 단계별 messageText(§7.6). 그룹 설정 `[단계 엔티티, skip]`과 `skip_answer` 엔티티는 유지한다 | 재설정함, **봇 테스트 결과 미확인** |

- 위 2·4는 §7.6 Step 0의 3(단독 `{job_name}` 인식)과 5(그룹 파라미터 통과) 항목의 실제 시험에 해당한다. 결과는 확인되는 대로 이 표에 적는다.
- Step 0의 1(입력 컨텍스트 우선순위)은 발화를 블록마다 고유하게 재설정해서 **해당 없음**이 됐다. 다만 `직종 입력`·`판정 사례 찾기`가 단독 패턴을 잃은 뒤에도 평소 직종 단어(`용접`)가 의도한 블록으로 가는지는 T44에서 확인한다.

### 7.7 직종으로 찾기 시나리오 (독립 시나리오안)

**블록 4개**(판정 사례 검색의 `다른 사례 보기`·`처음으로`는 재사용).

| 블록 | 발화 | 입력 컨텍스트 | 스킬 | 출력 컨텍스트 | 응답 |
|---|---|---|---|---|---|
| ① 시작 | `직종으로 찾기`, `직종 검색`, `직업으로 찾기` | 없음 | 없음(정적) | `job_kw`(수명 1, 10분) | 안내 + 예시 바로연결(`조리`, `용접`, `청소`, `경비`, `운전`) |
| ② 직종 입력 | `{job_name}`, `{job_name} 일해요`, `{job_name}이요` 등 엔티티 태깅 문장(**엔티티 방식, 기본**) | `job_kw` | `직종 검색`(파라미터 이름 `keyword`, 엔티티 `job_name`, 값 `$keyword`) | `job_kw` | 스킬데이터 |
| ③ 직종 선택 | `직종 선택`, `직종 더 보기` | 없음 | `직종 검색` | `job_kw` | 스킬데이터 |
| ④ 선택한 직종으로 찾기 | `선택한 직종으로 찾기` | 없음 | **판정 사례 검색** | 없음 | 스킬데이터 |

- ③과 ④는 서버 버튼의 `messageText`와 **정확히 같은 문장**을 발화로 등록해야 한다(§7.4와 같은 규칙). ③·④ 블록에는 **필수 파라미터를 두지 않는다**(바로연결은 엔티티를 다시 추출하지 않고, 값은 `clientExtra`로 온다).
- ①·②·③은 출력 컨텍스트 `job_kw`를 **선언**해야 서버가 매 응답에서 입력 대기를 다시 걸 수 있다.
- 웰컴·도움말·폴백에 `직종으로 찾기` 바로연결을 추가한다. 서버도 조건이 없을 때 이 버튼을 보낸다.
- 개인정보 입력 금지 안내는 ①에 둔다.

**엔티티 방식이 기본이고 자유 입력은 선택이다**

| | 엔티티 방식(기본) | 자유 입력(선택, J0) |
|---|---|---|
| 카카오에서 동작 보장 | 문서로 확실(기존 `job_name` 엔티티) | **미검증** |
| 발화 원문 | 서버가 읽지 않음. 개인정보 원칙 유지 | 서버가 읽음. Rails `Parameters:` 로그에 원문이 남아 **출시 전 로그 필터 필수**(§10.2) |
| 인식 범위 | 사전 단어만(대표 54개 + 동의어 223개) | 어떤 단어든 부분 일치 |
| 말투·조사 | 카카오가 처리(`용접일 해요` → `용접공`) | 직접 정리(`JobKeyword`) |
| 약점 | 사전에 없는 직종은 인식 안 됨. 직종 이름이 25,077가지라 사전은 직종이 있는 사례의 약 70%를 덮는다 | 폴백이 가로채는 위험, 연결 방법 자체가 미확인 |
| 서버 | 대표를 사전 핵심어로 확장(§3.5) | 컨텍스트가 있을 때만 발화를 검색어로 사용 |

- **②는 `{job_name}` 패턴으로 만든다.** 파라미터를 이름 `keyword`, 엔티티 `job_name`, 값 `$keyword`로 만든다(값 칸의 `$`는 엔티티가 아니라 **파라미터 이름**을 가리킨다). 서버의 `action.params.keyword` 경로가 이를 받고 대표 엔트리로 확장한다. 예시 바로연결(`조리`, `용접` …)도 이 경로로 동작한다.
- **발화는 다른 블록과 겹치면 안 된다(§7.5 6).** 위 ②의 `{job_name}` 단독 패턴은 단계별 답변1(§7.6)이 쓰므로 `직종 입력`에는 `직종 {job_name}`처럼 **단독이 아닌 형태**를 쓴다(제안, 시험 전). 입력 컨텍스트 `job_kw`는 입력 대기 상태를 표시하는 용도로 유지하되, 같은 발화를 컨텍스트로 구분하는 데는 쓰지 않는다. **재설정한 실제 발화는 기록하지 못했다.**
- **J0(자유 입력, 선택):** 사전에 없는 직종까지 받으려면 임의의 문장이 블록에 도달해야 한다. 제공된 문서에는 자유 문장을 받는 시스템 엔티티가 없고, 폴백 블록에 스킬을 연결하는 방법도 적혀 있지 않다. 폴백 블록에 스킬 연결이 되는지, 입력 컨텍스트만으로 발화 패턴 없이 블록에 도달하는지를 확인해서 되면 추가한다. 서버는 이미 `job_kw` 컨텍스트가 있을 때 발화를 검색어로 읽는다. **안 되더라도 엔티티 방식만으로 기능은 완성된다.**

**알려진 제약**
- 후보는 판정서에 적힌 표기라 `생산직`, `건설 및 광업 단순 종사원` 같은 직업분류 항목명도 섞여 나온다. 대표 엔트리별 후보가 200개 상한에 닿는 경우가 22개 있다(상위 200개만 쪽으로 보여 준다).
- 선택은 최대 10개다. 버튼의 `extra`에 담아 이어 가므로 `extra` 크기 제한이 문서에 없다(10개 × 30자 이하라 작다).
- 선택 직종만으로 찾는다. 신체부위·질병·판정 같은 다른 조건을 함께 줄 수 없고, 결과 아래 `조건 바꾸기`·`단계별로 찾기`로 다시 시작한다.

### 7.8 직종 검색을 어디에 붙일까: 독립 시나리오 vs 단계별 첫 질문(비교)

서버의 직종 검색 스킬은 두 방식에서 **똑같이** 쓴다. 차이는 카카오 쪽 구성이다.

| | A. 독립 시나리오 `직종으로 찾기` (§7.7) | B. 단계별 사례 찾기의 첫 질문(직종)에 포함 |
|---|---|---|
| 흐름 | 직종 입력 → 후보 선택(여러 개) → 사례 | Q1에서 직종 입력 → 후보 선택 → **이어서 Q2~Q5(신체부위·질병·작업·판정)** → 사례 |
| 새로 만들 블록 | 4개 | 단계별 블록 6개에 직종 선택용 3~4개 추가, 단계마다 파라미터 누적 항목 추가 |
| 고른 직종을 넘기는 방법 | 결과 버튼의 `extra`(`job_names`) | 단계별 컨텍스트 `wizN`로 넘겨야 함. 컨텍스트 `params`는 문자열만 담을 수 있어 배열을 JSON 문자열로 직렬화하고 서버가 `action.params`에서 풀어 읽도록 **서버 수정 필요**(지금은 `clientExtra`에서만 읽음) |
| 의존하는 미검증 동작 | **입력 컨텍스트 블록의 우선순위** 1가지(자유 입력은 선택 사항) | 위 1가지 + **단계별 Step 0의 나머지**(`#wizN.*` 참조, 컨텍스트 수명) + **스킬 응답으로 컨텍스트 값 설정**(블록에 미리 선언된 출력 컨텍스트만 갱신 가능), 합쳐 3가지 |
| 직종 외 조건과 결합 | 불가(직종만) | 가능 |
| 직종이 모호한 사용자 | 후보를 보고 고름 | 후보를 보고 고름 |
| 흐름이 끊길 위험 | 낮음(상태가 `extra`로 완결) | 높음(컨텍스트 수명·폴백 개입·만료가 단계 수만큼 겹침) |
| 디버깅 | 봇 테스트에서 요청·응답으로 확인 | 컨텍스트 값이 단계마다 누적되어 어디서 비는지 추적이 어려움 |
| 기존 흐름에 영향 | 없음 | 단계별 Q1 블록 구조가 바뀜 |
| 제공 가치 | 직종 하나로 빠르게 찾기 | 직종을 후보로 정확히 고른 뒤 다른 조건까지 좁히기 |

**권장:** A를 먼저 한다. 의존이 가장 적고 서버 스킬을 그대로 쓰며 단계별 흐름과 독립적으로 검증·배포할 수 있다. 이후 단계별 Step 0 결과가 좋으면 B로 확장한다. 그때 서버는 `action.params`의 직종 배열 읽기와 컨텍스트 값 설정만 더하면 되고, 후보 선택 화면은 그대로 재사용한다.

## 8. 발화 패턴

`{파라미터:값}`은 그 단어를 해당 엔티티로 태깅한다는 뜻이다. 값은 엔티티 사전의 대표 엔트리 또는 동의어를 쓴다. 문장마다 태깅 결과와 어순을 달리해 등록한다. 모두 **판정 사례 찾기** 블록(④)에 등록한다.

| 유형 | 발화 |
|---|---|
| 시작(엔티티 없음) | `판정 사례 찾기` / `사례 찾아줘` / `판정 사례 검색` / `비슷한 사례 알려줘` / `산재 사례 보여줘` |
| 질병만 | `{disease_name:회전근개 파열} 사례 찾아줘` / `{disease_name:허리디스크} 판정 사례 보여줘` / `{disease_name:손목터널증후군} 걸렸는데 비슷한 사례 있나요` / `{disease_name:뇌경색} 산재 사례 알려줘` |
| 질병 + 판정 | `{disease_name:회전근개 파열} {decision_type:불인정} 사례` / `{disease_name:허리디스크} {decision_type:인정}된 사례 보여줘` / `{disease_name:손목터널증후군} {decision_type:일부인정} 사례 있어?` / `{disease_name:뇌경색} {decision_type:불인정} 판정 알려줘` |
| 직종만 | `{job_name:택시기사} 사례 찾아줘` / `{job_name:경비원} 판정 사례 보여줘` |
| 직종 + 질병 | `{job_name:용접공}인데 {disease_name:허리디스크} 진단받았어요` / `{job_name:조리원} {disease_name:손목터널증후군} 사례` / `{job_name:환경미화원} {disease_name:회전근개 파열} 판정 사례 찾아줘` |
| 직종 + 질병 + 판정 | `{job_name:조리원} {disease_name:손목터널증후군} {decision_type:인정} 사례` / `{job_name:용접공} {disease_name:허리디스크} {decision_type:불인정} 사례 보여줘` |
| 판정이 앞 | `{decision_type:불인정}된 {job_name:용접공} {disease_name:허리디스크} 사례` / `{decision_type:인정}받은 {job_name:조리원} 사례` |
| 직종 + 작업요인 | `{job_name:조리원} {work_factor:반복 동작} 때문에 아픈 사례` / `{job_name:물류 노동자} {work_factor:중량물 취급} 사례 찾아줘` |
| 작업요인 + 질병 | `{work_factor:중량물 취급} 하다가 {disease_name:허리디스크} 생긴 판정` / `{work_factor:반복 동작} {disease_name:회전근개 파열} 사례` |
| 작업요인만 | `{work_factor:쪼그려 앉기} 작업 사례` / `{work_factor:야간·교대근무} 관련 사례` |
| 판정만 | `{decision_type:불인정} 사례만 보여줘` |

- 총 30문장 내외다. 봇 테스트에서 매칭에 실패한 문장을 추가해 가며 늘린다(튜토리얼 권장).
- `다른 사례 보기`, `검색 조건 바꾸기`, `처음으로`, `도움말`, 승인 가능성 문의 문장은 해당 블록(⑤⑥②③⑦)에 따로 등록한다.
- "판정만" 유형은 질병·직종·작업이 없어 되묻기가 나간다. 되묻기 응답 후 `decision_type` 값이 유지되는지 확인한다(§9 T9).

## 9. 봇 테스트 시나리오

관리자센터의 봇 테스트(Ctrl+E)에서 실행한다. 상세 정보 영역에서 **반응한 블록, 인식된 패턴, 추출된 파라미터, 스킬명**을 볼 수 있고, 더보기에서 스킬 요청·응답 전문과 응답 오류를 볼 수 있다.

| # | 입력 | 기대 블록 | 기대 파라미터 | 확인할 점 |
|---|---|---|---|---|
| T1 | `판정 사례 찾기` | 판정 사례 찾기 | 없음 | 되묻기 질문이 나간다 |
| T2 | (T1 이후) `회전근개 파열` | 판정 사례 찾기 | `disease_name`=회전근개 파열 | 되묻기 응답으로 값이 채워지고 스킬이 호출돼 사례 목록이 나온다 |
| T3 | `회전근개 파열 사례 찾아줘` | 판정 사례 찾기 | `disease_name`=회전근개 파열 | 되묻기 없이 바로 스킬 호출 |
| T4 | `회전근개파열 사례 찾아줘` (붙여쓰기) | 판정 사례 찾기 | `disease_name`=회전근개 파열 | **띄어쓰기 변형이 인식되는지**(§6.6). 안 되면 사전 변형 추가 |
| T5 | `허리디스크 불인정 사례` | 판정 사례 찾기 | `disease_name`=추간판 탈출증, `decision_type`=**불인정** | **`인정`으로 잘못 추출되지 않아야 한다** |
| T6 | `일부인정 사례 보여줘` | 판정 사례 찾기 | `decision_type`=**일부인정** | `인정`이 아니어야 한다. 조건이 없어 되묻기가 나간다 |
| T7 | `용접 일 하는데 허리디스크 진단받았어요` | 판정 사례 찾기 | `job_name`=용접공, `disease_name`=추간판 탈출증 | 동의어(용접, 허리디스크)가 대표 엔트리로 바뀐다 |
| T8 | `조리원 반복 동작 사례` | 판정 사례 찾기 | `job_name`=조리원, `work_factor`=반복 동작 | 사전의 `work_factor`가 추출된다 |
| T9 | `불인정 사례만 보여줘` → `회전근개 파열` | 판정 사례 찾기 | `decision_type`=불인정, `disease_name`=회전근개 파열 | 되묻기 후에도 먼저 받은 `decision_type`이 유지된다 |
| T10 | `허리디스크랑 회전근개 사례` | 판정 사례 찾기 | 확인 필요 | 같은 엔티티 두 개가 어떻게 추출되는지 기록한다 |
| T11 | `어깨가 너무 아파요` | 폴백 또는 되묻기 | 확인 필요 | 사전에 없는 증상 표현의 처리 방식 기록 |
| T12 | `산재 될까요?` | 승인 가능성 문의 | 없음 | 승인 여부를 단정하지 않고 사례 검색을 안내한다 |
| T13 | `처음으로` | 처음으로 | 없음 | 안내와 바로연결이 나온다 |

## 10. 로깅·개인정보 작업

### 10.1 현재 상태(개발 테스트 기간)

- 챗봇 컨트롤러가 직접 남기는 로그(`kakao_search`)는 요청 ID, 결과 건수, 상한 도달 여부, 폴백 여부, 처리 시간만 기록한다. 발화 원문과 추출 값은 남기지 않으며 테스트로 확인한다.
- **Rails 기본 `Parameters:` 로그에는 `utterance`, `botUserKey`, `plusfriendUserKey`, 추출된 엔티티 값이 남는다.** 개발 테스트 동안 디버깅을 위해 이대로 둔다.
- 웹 검색의 `log_search_event`가 `params[:q]` 원문을 기록한다. 개발 테스트 동안 유지한다.

### 10.2 출시 전 처리(출시 차단 조건)

개발계획 §7의 출시 차단 조건("응답·로그에 입력 원문이 남는다")에 해당한다. 공개 전에 아래를 처리한다.

- [ ] `config/initializers/filter_parameter_logging.rb`의 `filter_parameters`에 `utterance`, `userRequest`, `botUserKey`, `plusfriendUserKey`, `appUserId`와 엔티티 키(`disease_name`, `job_name`, `work_factor`, `q` 등)를 추가한다. 중첩 JSON 본문이 걸러지는지 로그로 확인한다.
- [ ] `log_search_event`에서 `query: params[:q]`를 제거하고 길이만 남긴다. 해시는 같은 질의를 추적할 수 있어 권하지 않는다.
- [ ] **직종 검색 스킬은 `userRequest.utterance`를 검색어로 읽는다**(§3.5). 직접 쓰는 로그에는 남기지 않지만 Rails 기본 `Parameters:` 로그에는 발화 원문이 남으므로, 위 `filter_parameters`에 `utterance`가 반드시 들어가야 한다.
- [ ] 이미 쌓인 개발 기간 로그의 보관·삭제 방침을 정한다.

### 10.3 데이터

- 데이터는 모두 비식별 처리가 끝난 상태로 보고 전체를 공개 대상으로 본다. 비식별은 적재 단계의 책임이다.
- `PublicCase`는 허용 필드만 직렬화하고, 서술 필드(`job_summary`, `reasoning_summary`)에는 `PIIMasking`을 적용한다. `PIIMasking`은 주민번호·전화번호·이메일·계좌번호 **형태**만 가리며 이름·주소는 걸러내지 못한다.
- 비식별 누락 표본 점검은 출시 전 작업이다(§12.2).

- [ ] 비식별 누락 표본 점검(`job_description`, `main_reasoning` 등 사용 필드)
- [ ] 판정 결과가 모든 표본에서 원본 판정서(`case_no`)와 일치하는지 확인
- [ ] 운영 데이터에서 엔티티 건수·응답 시간 재측정(5초 제한 대비). 신체부위 조합은 개발 노트북에서 최대 약 0.8초(§6.7)

## 13. 남은 작업 목록

우선순위는 위에서 아래 순서를 권한다.

0. **진행 중인 장애 처리:** `모르겠어요` 미진행·폴백 증상 확인(§7.6 표), 운영 재시험(§6.8), 필요하면 FTS 예열과 처리 시간 상한 추가.
1. **엔티티 업로드 확인**(§6.6). 특히 "불인정" 추출과 동의어 분리, 열 수 제한. `body_part.csv`, `skip_answer.csv`도 올린다.
2. **블록·발화 입력**(§7, §8): 관리자센터에서 직접 구성한다. 단계별 사례 찾기는 **Step 0(§7.6)을 먼저** 한 뒤 블록 6개를 만든다.
3. **봇 테스트 실행**(§9)과 결과 기록. 매칭 실패 발화는 §8에 추가한다.
4. **서버 검색 확장**(신체부위는 §6.7에서 완료): 공백을 무시하고 한 개념의 여러 표기를 `OR`로 검색한다. 사전의 `db` 목록을 매핑 자료로 쓴다. 단계별 사례 찾기에서 질병·직종·작업을 고르면 결과가 적게 나올 수 있어 이어서 하는 것을 권한다.
   - `disease_name`, `job_name`: 대표 엔트리 → `db` 패턴들(공백 무시 `LIKE ... OR ...`). 웹 검색 화면은 건드리지 않는다.
   - `work_factor`: 대표 엔트리 → `q` 변형들(`OR`).
   - `decision_type`은 필요 없다.
   - 효과는 §6.5의 표에서 대표어만 검색할 때와 변형 합집합의 차이다.
5. **조건 변경 흐름(`CASE_REFINE`)**: `검색 조건 바꾸기`에서 이전 조건을 유지하는 방식. 컨텍스트와 서버의 `contexts` 처리가 필요하다(결정 §14).
6. **산재 신청 절차 안내(`GUIDE`)**: 공식 출처·적용일·검토일을 연결해야 한다. 자료 관리 책임자와 갱신 주기가 먼저 정해져야 하며, 웰컴·도움말에 버튼을 추가한다.
7. **구조화 필터 도입 검토**: 중량물 취급(`heavy_lifting`)과 부담 부위(`burden_body_part`)는 구조화 컬럼이 있어 전문 검색보다 정확하다.
8. **상세 설명 보강**: 현재는 사례 목록과 웹 링크만 제공한다. `reasoning_summary`는 DTO에 있으나 응답에는 쓰지 않는다. LLM을 쓰더라도 입력은 공개 DTO 범위로 제한하고 근거 없는 판정 이유를 만들지 않는다.
9. **직종으로 찾기**: 스킬 등록(§5.5) → 블록 4개 입력(§7.7, 엔티티 방식) → 봇 테스트 T33~T46. 자유 입력(J0)은 선택이고, 단계별 첫 질문에 붙이는 확장은 단계별 Step 0 뒤에 판단한다(§7.8).
10. **평가 세트와 출시 전 로깅 정리**(§10.2, §12.2)

| 1 | 서버 검색 확장을 지금 진행할지 | 권장. 엔티티 4종의 재현율이 크게 좌우된다(§6.5) |
